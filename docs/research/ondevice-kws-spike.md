# 逐词实时标注：KWS 可行性 spike（2026-10）

> 一句话：**可行 ✓** —— 用 4.4MB 的关键词检测模型，在**真人录音**上把**全部实词**逐词命中。
> 端侧与服务端**都能跑**（性能不是瓶颈）；差别只在架构与成本。

## 要解决的问题

朗读页需要「**用户读到哪里了**」（逐词实时标注）✓ 而不是"这一句打几分"。

⚠️ 这两件事**难度差一个量级**，而本仓库此前的端侧调研只覆盖了**后者**（GOP / 音素后验打分
⇒ 结论"不现实" ✓ 那个结论是对的 ✓ 但**不适用于前者** ✗）：

| | 需要什么 | 难度 |
|---|---|---|
| 打分（GOP） | 声学后验 + 强制对齐 + 分数校准 | ⚠️ 高（见 on-device-capability.md） |
| ⭐ **逐词标注** | **已知文本**上的关键词命中 | ⭐ **低** |

⭐ 关键前提：**参考文本是已知的** ✓ ⇒ 这不是通用识别，是 **open-vocabulary keyword spotting** ✓

## 选型：sherpa-onnx KWS（Apache-2.0 ✓）

| 项 | 值 |
|---|---|
| 模型 | `sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20`（**中英文** ✓） |
| 体积 | encoder int8 **4.4MB** + decoder 743KB + joiner 85KB + tokens 1.9KB + en.phone 3.2MB |
| 延迟 | chunk-8 ⇒ **160ms** 一块（chunk-16 是 320ms，准确率略高） |
| 许可证 | **Apache-2.0** ✓（对比：mp3 编码器 lamejs 是 LGPL ✗） |
| 关键词 | **任意指定** ✓（`text2token` 转音素；英文用 `en.phone` 词典 ✓） |

## 实测（本地 Node，真机录音）

环境：`sherpa-onnx-node@1.13.8`，Node 20（⚠️ **Node 24 会报 `External buffers are not allowed`** ✗），macOS arm64。

**① 官方测试音频**（机制验证）

```
en_0.wav（6.6s, RTF 0.014）⇒ LIGHT_UP
en_1.wav（16.7s, RTF 0.013）⇒ LOVELY_CHILD
zh_3.wav（8.0s,  RTF 0.014）⇒ 文森特卡索 | 法国     ← 一段音频命中【两个】关键词 ✓
```

**② 真人录音 + 我们自己的句子**（准确率验证）

```
句子   Everything should be made as simple as possible, but not simpler.  （11 词）
录音   .uploads/audio/06ef2b193b83b3d7/315/1790526865657.mp3（7.14 秒，真实用户）

命中 7 个：EVERYTHING · SHOULD · MADE · SIMPLE · POSSIBLE · BUT · SIMPLER
漏掉 3 个：BE · AS · NOT          ← ⚠️ 全是【最短的虚词】（1~3 个音素）
```

⭐ **实词一个不漏** ✓ —— 而"读到哪儿了"靠的正是实词这些锚点 ✓
⭐ 命中顺序**就是朗读顺序** ✓ ⇒ "读到第几个词"直接可读 ✓
⚠️ `startTime` 字段实测恒为 **0.00** ✗ ⇒ **不能靠时间戳**定位，要靠**到达顺序** ✓

## 两个已知坑（都会让人白花半天）

1. ⚠️ **Node 24 跑不了** ✗ —— 原生插件给的是 napi 外部内存，Node ≥22 会拒收
   （`External buffers are not allowed`）⇒ 用 **Node 20** ✓
2. ⚠️ **官方示例的"尾填充"**（喂 0.4 秒静音）是为了 flush 最后一个词 ✓
   用流式接口的 `inputFinished()` 等效 ✓（但 Node 24 下连它也会撞上上面那个问题）

## ⚠️ 还没验的（做之前必须知道）

| 项 | 状态 |
|---|---|
| **端侧 WXWebAssembly** | ❌ **未验** —— `WXWebAssembly` 存在 ✓（v2.13.0+ ✓ `.wasm.br` ✓）但**无多线程/SIMD 承诺** ✗；sherpa 的 WASM 是给浏览器编的 ✗ |
| **服务端实时** | ⚠️ 需要**边录边传**（长连接 ✓）—— 架构改动大 ✗ |
| **虚词命中** | ⚠️ 短虚词（be/as/not）漏 ✓ —— 若"逐词"要求含虚词，需要更小的 chunk 或更高阈值调参 |
| **中式英语口音** | ⚠️ 只测了**一条**真人录音 ✓ 样本太小 ✗ |

## 结论与建议

| 问题 | 答案 |
|---|---|
| 逐词实时标注能做吗？ | ✅ **能** —— 真人录音上实词全中 ✓ |
| 性能是瓶颈吗？ | ❌ **不是** —— RTF 0.014（快 70 倍）⇒ 手机慢 50 倍也够实时 ✓ |
| 许可证干净吗？ | ✅ **Apache-2.0** ✓ |
| 放服务端还是端侧？ | ⭐ **服务端已验证可行** ✓；端侧**待验 WXWebAssembly** ✓ |

⭐ 建议顺序：**先用服务端把功能做出来**（已验证 ✓ 风险最低 ✓），
  同时单独验端侧 WASM ✓ —— 端侧成了再搬过去（零成本零延迟 ✓），不成也不影响功能 ✓
