# 「看视频广告换能量」通道调研

> 调研问题（用户 2026-10 提）：
> ① 现在能量只能靠虚拟支付买，想加一条**看视频广告免费得能量**的通道 —— 怎么接、依赖什么条件？
> ② 看一次广告补多少能量，成本账怎么算？
>
> **标注约定**：✅ 官方原文/官方文档 · 🔶 估算或由官方数字换算 · ❓ 未找到官方依据（行业经验值）。
> 本文件是**调研结论**，不承担「做没做」——任务状态见 [plan.md](../../plan.md)。

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| **能不能接** | ✅ **能，但只有一条合规路**：小程序**流量主 → 激励视频广告**（`wx.createRewardedVideoAd`）。小程序内**接不了**穿山甲 / 优量汇 / TradPlus 这类第三方广告 SDK（它们只有 App 形态；微信小程序广告只走微信自己的广告组件） |
| **现在能不能开** | ❌ **不能**。门槛是**累计独立访客 UV ≥ 500 + 无刷粉/无严重违规** ✅（微信广告运营专员 2026-03 答复；旧/代运营口径是 1000，两套都在线）—— 本项目**尚未上线、主体类型未定**（plan.md A2）⇒ 这条通道今天连入口都没有，**不是技术问题，是资格问题**。⚠️ 资格**次日刷新** |
| **前置依赖（省不掉）** | **ICP 备案**（2023-09 起小程序备案才能上架 ⇒ 要「已上线」就绕不开）+ 已上线 + **UV 破 500** + 后台配好**财务信息**（个人绑本人储蓄卡、企业签对公+开票；不配会卡住结算）。⚠️ 区别：**微信认证只有虚拟支付强制**，流量主无此明文要求 ⇒ 备案是两条路的**公共前置**，认证只挡虚拟支付。个人主体也能开流量主并收款（免发票、代扣个税） |
| **一次广告挣多少** | ⭐ **后台 eCPM 是到手口径**（已扣平台分成：官方 5:5，📌 实证「广告主 15 元/千次 → 后台显示 7.5」）。工具/学习类激励视频到手 eCPM 🔶 **10–60 元/千次** ⇒ **每看完一次到手 ≈ ¥0.01–0.06，中位 ¥0.02–0.04**（小游戏官方口径 >50 元，是我们的 1.5–2 倍）。⚠️ 没有合适广告（1004）就 0 收入 |
| **一次补多少能量** | ⭐ **1 点 / 次**（≈半次挑战）。保本线：**1 点/次要求到手 eCPM ≥ 60**（正好是现实区间的上沿）⇒ 现实里 1 点/次是「**略亏 → 打平**」；**2 点/次要求到手 eCPM ≥ 120，是现实的 2–6 倍，做不到** ⇒ 不给。**日上限 2–3 点**，且**只在「余额不足一次挑战」时给出入口** |
| **真正的约束不是钱** | 评测成本 ¥0.0015–0.006/次（≈0.4 分钱），广告收入比它高一个量级 —— **按增量成本算，这通道稳赚**。亏不亏取决于**机会成本**：白送的每一点，都是本来可能卖 ¥0.06–0.10 的点 ⇒ 所以规则必须是「只发给**不会付钱**的人 + 限额」，而不是「人人可刷」 |
| **最大风险** | ✅ **已核清：不违规**——《运营规范》5.13 虚拟支付约束的是「**购买和支付**」通道（钱必须走 xpay），**不是免费获取途径**；5.33「绕开虚拟支付」打击的是引导用户去**外部充值/购买**；5.34 打击的是「**自动弹出广告页面**诱导或强制观看」（用户主动点按钮不在其列）；官方激励视频文档本身就写「`res.isEnded` → **可以向用户下发奖励**」。⚠️ 但三条**原文红线**必须避开：**① 未完全播放就发奖 ② 承诺了不发 ③ 设计「付费免广告」/自设关闭逻辑**（见 §5.2） |
| **服务端能验证「真看完」吗** | ⚠️ **官方有这套能力，但小程序侧能不能用要实测**：官方《激励广告服务端验证接入指引》要求客户端 `show()` 前调 `setServerSideVerificationData`、服务端收 AES-256-CBC 回调验签，**基础库 ≥ 3.10.3**（2025-09 才发布的版本）；但该指引挂在**小游戏**目录下，而**小程序 API 参考里没列这个方法** ⇒ 必须实测/问微信广告客服。**没有 SSV 时**发放依据只能是客户端上报（§3.3） |

## 1. 现状：这条通道要接进什么系统

| 事实 | 值 | 出处 |
|---|---|---|
| 能量是**虚拟货币**（不是次数），花点数换挑战 | 每次挑战 **2 点** | `packages/shared/src/constants/index.ts`（`ENERGY_PER_CHALLENGE`） |
| 免费用户每日**惰性补足** | `max(energy, 3)` ⇒ 每天白送 1.5 次挑战 | `apps/server/src/services/energy.ts:58`（`topUpEnergy`） |
| 零售价 | 10 点 ¥1（¥0.1000/点）· 300 点 ¥20（¥0.0667/点）· 3000 点 ¥180（¥0.0600/点） | `ENERGY_PACKS`；[../design/payment-and-purchase.md](../design/payment-and-purchase.md) §2.1 |
| 每次挑战的**评测成本** | **¥0.0015–0.006**（讯飞 ISE，30 秒音频 1 次）⇒ **每点 ¥0.00075–0.003** | [speech-eval-vendor-comparison.md](speech-eval-vendor-comparison.md) §0、[../design/payment-and-purchase.md](../design/payment-and-purchase.md) §2.4 |
| 能量的账本 | `energy_ledger`，**幂等键 = (reason, ref_type, ref_id, user_id)**，余额 `users.energy` 是缓存 | `apps/server/src/services/energy.ts:183`（`addEnergy`） |
| 现有的 `reason` 枚举 | `daily_topup / challenge_hold / challenge_release / purchase / admin / streak_makeup` | `energy.ts:28`（`ENERGY_REASON`） |
| 卖能量必须走**小程序虚拟支付** | 普通微信支付卖虚拟货币属违规 | [../design/payment-and-purchase.md](../design/payment-and-purchase.md) §1.1 |
| 上线/主体状态 | ⚠️ **未上线；主体类型个人/个体户/企业未定** | plan.md A2 |

⭐ **结论：广告发放不需要任何新表新机制**——就是 `addEnergy()` 多一个 `reason`：
`reason='ad_reward'`、`refType='ad'`、`refId=服务端下发的一次性券`。
现有幂等键天然挡住「重放 / 并发 / 用户重复点」。**这是本项目最省事的一处**（§3.2）。

**入口该放哪（现成的两个钩子）**：

1. ⭐ `apps/miniprogram/src/pages/reading/reading.ts:1797` 的 `ENERGY_EXHAUSTED` 分支 ——
   现在的文案是「能量不够了（还差 N 点）—— 明天会补到 3 点，也可以充值」。
   这是**最精准的广告场景**：用户当下就想读完这一句，只差 1–2 点。
   加一个按钮「看视频 +1 点」即可，不需要改服务端契约（余额由 `readEnergy` 给）。
2. `apps/miniprogram/src/pages/me/energy/`（余额 + 充值 + 流水页）—— 给「主动攒点」的用户。

## 2. 通道选型：有哪些路，哪条能走

| 通道 | 能不能走 | 依赖 | 单价量级 | 判断 |
|---|---|---|---|---|
| ⭐ **小程序流量主 → 激励视频** | ✅ **唯一合规路** | UV ≥ 1000、已上线、备案、财务信息 | eCPM 🔶 30–150（工具类 30–80）；到手 ×50% | **就走这条**；门槛是资格不是技术 |
| 小程序内接**第三方广告 SDK**（穿山甲/优量汇/TradPlus） | ❌ 不可行 | — | — | 这些 SDK 只有 **App** 形态；小程序内广告只能用微信自己的广告组件（第三方中介平台支持的是「App 广告落地到小程序」，👉 不是在小程序里放广告） |
| **H5**（微信内打开网页放广告） | ❌ 不可行 | — | — | 微信内 H5 拿不到激励视频组件；AdSense 在中国大陆不可用 |
| **独立 App**（穿山甲/优量汇/AdMob 激励视频） | ✅ 可行，但贵 | 上架应用商店 + 软著 + 广告平台账号 + 一套 App | eCPM 通常高于小程序，iOS 更高 | spec.md 已论证过「转 App 成本主要在 UI 重写」—— 但**现在不该为广告做 App** |
| **积分墙 / 任务墙**（下载 App、注册得奖励） | ❌ 不建议 | — | 单任务 ¥0.5–5（高得多） | 小程序内**跳转外部下载/注册**是高风险场景（诱导、绕开微信生态），与虚拟支付合规叠加后风险不可控；收益高但不值得赌 |
| **非广告的免费能量**（签到/邀请/连战/每日任务） | ✅ 已有基础 | 无门槛 | 纯成本（每点 ≈¥0.003） | ⭐ **先做这个**：reward-system.md 已有触发器枚举与发放接口，零资质门槛、零合规风险（§6） |

⚠️ **一个必须先说清的现实**：流量主要 **UV ≥ 1000 的累计访问**，冷启动期（第一天到第 1000 个访客）
**一分钱广告收入都没有**。所以「广告换能量」不能当作上线时的能量来源，只能当作**破 1000 UV 之后的第二条管道**。
在破 1000 之前，免费能量的来源只能是「每日补足 3 点 + 签到/任务奖励」。

## 3. 接入依赖与步骤（问题 ①）

### 3.1 资格前置（不满足就别写代码）

| # | 条件 | 说明 | 现状 |
|---|---|---|---|
| 1 | 小程序**已发布上线** | 未上线没有 UV，也开不了流量主 | ❌ 未上线 |
| 2 | **累计独立访客 UV ≥ 500** 且无刷粉/无严重违规 ✅ | 微信广告运营专员 2026-03 答复的**最新口径**（个人/企业均可）；⚠️ 代运营通道旧口径仍写 **1000**，两套都在线 | ❌ 0 |
| 3 | **ICP 备案** | ⚠️ **实际省不掉**：2023-09 起新注册小程序须**先备案才能上架**，而流量主/虚拟支付都要求「已上线」；虚拟支付文档亦明写「已认证、已备案」 | ⏳ 未办 |
| 4 | **微信认证** | **只有虚拟支付强制**（流量主开通条件里没有这一条）⇒ 若只先做广告通道，这一步可以晚一点 | ⏳ 未办 |
| 5 | **主体类型** | 个人主体**也能**开流量主**并收款**（免发票、代扣个税；结算主体唯一、多账号收入合并出单）；但个人主体开不了普通微信支付 | ⚠️ **未拍板**（plan.md A2） |
| 6 | **财务信息配置**（后台：广告与服务 → 流量主 → 财务管理） | 不配会**卡住结算**；个人绑本人储蓄卡+身份证，企业要对公账户+开票信息 | ❌ 未配 |

⭐ **顺手办的事**：备案/主体/认证这一批材料，广告与虚拟支付**共用**（见 [../design/payment-and-purchase.md](../design/payment-and-purchase.md) §11.4）。
⇒ 顺序建议：**主体定下来 → 备案 → 上线 → 攒 UV**；认证可与后面几步并行，
⭐ 这样**流量主（UV 600 左右就能开）会比虚拟支付更早可用** —— 免费能量通道可以先上广告。

### 3.2 技术接入（小程序侧，四步）

1. **后台建广告位**：mp 后台 → 广告与服务 → 流量主 → 广告位管理 → 新建**激励视频**广告位 → 拿到 `adunit-xxx`。
   ⚠️ 广告位本身要过审（错误码 **1005 审核中 / 1006 被驳回 / 1007 封禁 / 1008 已关闭**）。
   ⚠️ 时长只有 **6–15s / 16–30s** 两档，且**同一小程序多个广告单元的时长设置必须一致**。
2. **客户端**（`wx.createRewardedVideoAd`；基础库要求：API 2.0.4 起、**小程序端实测要 ≥ 2.6.0**）：
   - ⚠️ **单例且只在当前页面有效、不可跨页面** ⇒ 在 `onLoad` 里创建，`onLoad/onError/onClose` **只注册一次**
     （重复注册会多次回调 ⇒ 会重复发奖的错觉，实际由服务端幂等挡住）；
   - `ad.onError(err)` → 提示「暂时没有广告，稍后再试」，**不要**把失败当成功；
     ⚠️ **1004 = 无合适广告**（很常见：官方示例的曝光率只有 ~0.41）⇒ **入口按钮必须依据 onLoad 成功状态展示**，
     否则用户点了没反应（这是最容易踩的体验坑）；
   - `ad.onClose(res)` → **`res.isEnded === true` 才算看完**（中途关掉不给）；
   - `ad.show()` 失败要走 `ad.load()` 重试再 `show()`（官方推荐写法）；可用 `preloadAd`（2.14.1+）预加载；
   - ⚠️ 开发者工具/未开通流量主时，广告必然会 `onError`（1000/1002 一类）——
     **本地联调必须留一条 mock 通道**，否则这条功能在本地根本走不通。
3. **服务端两个接口**（关键在设计，不在代码量）：
   - `POST /api/ads/ticket` → 校验资格（今日还剩几次）→ 落一行 `ad_tickets`（或直接复用一个内存/DB 券）→ 返回**一次性券 id**；
   - `POST /api/ads/reward { ticketId }` → 校验券未用/未过期 → `addEnergy({ reason:'ad_reward', refType:'ad', refId: ticketId, amount: 1 })` → 返回新余额。
   ⭐ 券是**服务端下发的**，这是把「客户端说了算」压缩到最小的唯一办法：
   客户端能伪造的是「我看完了」，但**伪造不出第二张没被用过的券**，也绕不过每日发券上限。
   ⭐ 若 SSV 在小程序侧可用（见 §3.3），则再加一条：微信回调 → 验签 → 落 `ad_rewards` → 券核销时才发能量。
4. **配置**：每日发放上限、单次点数走**落库配置**（与本项目 `goods` / `reward_rules` 同一套路：
   能被运营改的东西不要写死在代码里；改上限不该发版）。

### 3.3 「真看完」能不能在服务端验证？—— ⚠️ 官方有，小程序侧待实测

- ✅ **官方有服务端验证（SSV）**：`setServerSideVerificationData({userId, rewardItem, rewardAmount, customData})`
  （在 `show()` 前调用）→ 微信回调我们的 URL，参数含 `signature/timestamp/nonce/encrypt`，
  密文 **AES-256-CBC**，验签 = `sha256(Token + timestamp + nonce + encrypt)` 字典序拼接，回包给 `is_valid`；
  **超时 1s，重试 3 次（15s / 22.5s / 33.75s）**；配置入口：流量主后台 → 广告管理 → 激励广告 → **服务端奖励回调**；
  **基础库 ≥ 3.10.3**（2025-09-23 发布）；回调 URL 必须 http(s) 域名，**不接受 IP**。
- ⚠️ **但它挂在小游戏文档目录下**：`minigame/dev/guide/security/antiadcheat.html`，而**小程序 API 参考的
  RewardedVideoAd 方法列表里没有列出这个方法** ⇒ **小程序侧是否可用必须实测/问微信广告客服**。
  ❌ 不要按「小程序一定没有」或「一定能用」任一方向写方案 —— **两条路都要留出接口**。
- **没有 SSV 时的兜底**（都在我们自己的服务端，成本很低）：
  1. **一次性券**（§3.2）—— 挡住重放/并发/连点；
  2. **每日上限**（发券时就卡死，不是发完再检查）；
  3. **券的时限**（如 5 分钟，过期作废）—— 挡住「攒一堆券慢慢刷」；
  4. **与其它免费来源合并计数**（广告 + 签到 + 任务，一天合计不超过 N 点）—— 挡住「多入口叠加薅」；
  5. 观察指标：同一用户「广告完成率 100% + 每小时精确 N 次」这种机器节律，事后封人即可
     （成本极低，比事前风控划算）。
- ⚠️⚠️ **一条高压线（官方明文，二级违规）**：**「激励视频未完全播放（提前关闭），流量主照常下发奖励」是违规**，
  可冻结权限 7/15/30/90 天**并扣当月收入**。⇒ 实现上必须 `isEnded === true` 才发，且**失败要说清「没看完没有能量」**。

## 4. 成本账：看一次广告补多少能量（问题 ②）

### 4.1 先把三个口径分开（混着算必然吵起来）

| 口径 | 问题 | 答案的形状 |
|---|---|---|
| **A. 现金流**（增量） | 广告到手 − 评测成本 = ? | 广告 ¥0.02–0.04 vs 评测 ¥0.002–0.006 ⇒ **稳赚** |
| **B. 机会成本**（蚕食） ← ⭐ 真正的约束 | 白送的点 = 少卖多少钱？ | 1 点 = ¥0.06–0.10 的**零售价** ⇒ 广告常常**不够抵** |
| **C. 增长** | 免费用户多一次挑战 → 留存/转化 | 无法在这张表里算清，但它是这条通道的**主要理由** |

⭐ **一句话**：**「广告换能量」在会计上永远赚钱（A），在定价上经常亏钱（B）——
所以规则要按「机会成本」来设计：**只发到「余额不足」的场景 + 限额**（§4.5）。

### 4.2 收入侧：一次激励视频值多少

⭐ **先把口径钉死（这一条决定整段算得对不对）**：
✅ **流量主后台的 eCPM 是「到手口径」，已经扣过平台分成了** ——
- 官方分成规则：小程序激励视频「**100 万元以下流水 5:5 分成，100 万元以上 3:7（流量主 3 成）**」✅（《小程序激励式广告流量主指引》官方 PDF）；
- 开发者实证：**广告主出价 15 元/千次曝光 → 微信扣 50% → 后台 eCPM 显示 7.5** ✅（微信开放社区帖）。
⇒ ⚠️ **不要再把后台 eCPM 打五折**（打了就是重复扣）。
❓ 唯一要现场确认的是「2026 年后台展示的是不是仍是这个到手口径」——上线第一周看一眼结算页即可。

| 变量 | 值 | 备注 |
|---|---|---|
| 小程序（**非游戏**）激励视频 eCPM（到手） | 🔶 **10–60 元/千次**：工具/内容类经验区间 **20–60**；**工具类下限 10–15、上限 50–80** | ⚠️ 无官方公开值，来自教程/服务商/开发者实测（样本是自媒体帖，偏差大） |
| 对照：**小游戏** | ✅ 微信官方销售材料写激励式广告 **eCPM > 50 元** | 非游戏小程序通常是小游戏的 **1/1.5–1/2** ⇒ 我们按低档算 |
| **填充/曝光率** | ⚠️ **没有合适的广告就不展示，这次收入 = 0**（错误码 **1004**）；官方示例的曝光率（曝光/拉取）只有 **~0.41** | ⇒ **按钮要按 onLoad 成功状态出现**，否则用户点了没反应（体验坑，不是收入坑） |
| **大促波动** | 🔶 10 月中下旬电商预算较平日 **+50%~100%**，10.21–11.03 **+200%**，11.9–11.11 **+300%** | 我们控制不了；做预算时**别拿双 11 的数当基线** |
| 个人主体额外税 | 🔶 结算时代扣个人所得税 + 代征增值税及附加 ⇒ **到手再打约 8 折** | 企业主体开免税普票（小规模纳税人政策期内）可少这一层 |
| 结算 | ✅ 每月 15 号前结算上月收入、发**结算单**到预留邮箱；**企业**寄等额增值税发票后腾讯 30 个工作日打款；**个人**免发票、结算日后 30 个工作日内打款并**代扣代缴个税** | 🔶「半月结算」与「每月结算」两种说法并存；**无最低起结金额**属❓行业口径 |

**每次看完一次广告的到手收入**（= 后台 eCPM ÷ 1000；`isEnded === true` 才算有效曝光）：

| 到手 eCPM | 10 | 20 | 30 | 50 | 60 | 80 |
|---|---|---|---|---|---|---|
| **每次到手** | ¥0.010 | ¥0.020 | ¥0.030 | ¥0.050 | ¥0.060 | ¥0.080 |

⇒ ⭐ **现实预期：工具/学习类小程序，一次激励视频到手 ≈ ¥0.01–0.06，中位 ¥0.02–0.04。**
（这个数**不是**「看一次就赚一次」的期待值：拉取 100 次里可能只有 40 次真有广告。）

### 4.3 成本侧：一个能量点值多少钱

| 视角 | 单价 | 说明 |
|---|---|---|
| **真实边际成本** | **¥0.00075–0.003 / 点** | 讯飞 ISE ¥0.0015–0.006 ÷ 2 点 |
| **我们自己定的零售价** | **¥0.06–0.10 / 点** | 三档：¥0.1000 / ¥0.0667 / ¥0.0600 |
| **广告的等价交换率** | 1 次广告（到手 ¥0.01–0.06）↔ **0.17–1.0 点**（按 ¥0.06/点） | 见 §4.4 |

⭐ 两个成本差 **20–80 倍**——这正是「为什么必须按机会成本、而不是按评测成本来定价」。

### 4.4 保本线：一次广告最多能补几点

**保本上限公式**（按零售价口径，即「假设这些点本来会被买走」）：

```
E_max = 一次广告到手收入 ÷ 每点零售价
```

取**最高档单价 ¥0.06/点**（对用户最便宜的档、对我们最不利的档）：

| 到手 eCPM | 每次到手 | **E_max（保本）** | 判断 |
|---|---|---|---|
| 10 | ¥0.010 | **0.17 点** | ❌ 1 点都保不住 |
| 20 | ¥0.020 | **0.33 点** | ❌ |
| 30 | ¥0.030 | **0.50 点** | ❌ 差一半 |
| 50 | ¥0.050 | **0.83 点** | ⚠️ 接近打平 |
| 60 | ¥0.060 | **1.00 点** | ✅ **1 点/次刚好保本 = 现实区间的上沿** |
| 80 | ¥0.080 | 1.33 点 | ✅ 1 点/次有余 |
| 120 | ¥0.120 | 2.00 点 | ✅ 2 点/次才保本（**现实达不到**） |

⭐ **读法（这就是本题的答案）**：

- **1 点 / 次**：在现实到手 eCPM（10–60）下，广告只能抵掉这颗点价值的 **17%–100%**
  （中位 eCPM 30 时**正好抵一半**）⇒ 定位是「**用 0.5–1 倍的价格买一次「免费用户多读一句」**」，
  这是**可以接受的获客/留存支出**，但 ⚠️ **不要指望它赚钱**。
- **2 点 / 次（= 一次挑战）**：要**到手 eCPM ≈ 120** 才保本 —— **是现实区间的 2–6 倍，做不到** ⇒ ⚠️ **不给 2 点**。
  这一点和直觉相反（很多人想「看一次给一次挑战」），但账很清楚：
  **一次挑战卖 ¥0.12–0.20，一次广告只值 ¥0.01–0.06。**
- **0.5 点 / 次**（账上最漂亮）**做不到**：能量是**整数点**（`energy` 是 int；见 growth-and-energy.md §2
  「发放无最小刻度，1 点有意义」）⇒ **用「次数」而不是「单次点数」来调节**：**1 点 × 每天最多 2–3 次**。
- 相反地，**按「现金流口径」1 点/次的毛利率仍然有 70–95%**（收入 ¥0.01–0.06 vs 评测成本 ¥0.003+税）
  ⇒ **真正要防的不是"亏钱"，是"把付费用户变成看广告的用户"**：后者亏的是 ¥0.06–0.10/点，不是 ¥0.003/点。

### 4.5 ⭐ 推荐档位（按「机会成本口径」设计的规则）

| 规则 | 值 | 依据 |
|---|---|---|
| 单次发放 | **1 点**（不做 2 点） | §4.4：2 点要 eCPM 120，现实达不到 |
| 每日上限 | **2–3 次 / 人 / 天**（且与签到/任务**合并计数**） | 一天最多白送 1–1.5 次挑战，**低于每日补足的 3 点**，不破坏「能量稀缺」；⚠️ 也**远低于平台侧的限制**（见 §7 第 3 条：微信未公开上限，独立 App 的经验建议是 ≤15 次/人/日，且开发者实测「同位置看几次后就拉取失败」） |
| 触发条件 | ⭐ **只在余额 < 2（不足一次挑战）时给入口** | 这是「只发给不会付钱的人」的**可执行版本**：余额充足的人本来也不缺；也天然把入口放在成功率最高的挫败时刻（`reading.ts:1797`） |
| 付费用户怎么办 | ⚠️ **不要按「是否付费」分流**：条件只看**余额 < 2** | ① 财务上「余额<2」本身就是最好的筛选 —— 刚充过值的人自然不满足；② 合规上「付费用户看不到广告入口」容易被读成流量主规范明禁的「**付费免广告**」（§5.2 A-4）⇒ **不做付费/免费两种入口**，只做一种门槛 |
| 广告能量 **能不能替代充值** | ❌ **不能**：广告只能「补到够挑战一次」，不能攒成大额 | 否则「看 30 次广告 = 300 点（¥20）」会直接顶掉最大档商品 |
| 文案口径 | 「看个视频，补 1 点能量」 | ⚠️ 不写「免费」不写「薅」；**尤其不能写成「充值免广告」**（付费免广告是官方明禁的违规项，见 §5.2） |

### 4.6 DAU 1000 的规模感（🔶 假设：30% 的人每天看 1 次、10% 看 2 次 ⇒ 500 次/天）

| 项 | **eCPM 15（悲观）** | eCPM 30（中位） | eCPM 60（乐观） |
|---|---|---|---|
| 日广告曝光 | 500 次 | 500 次 | 500 次 |
| **日到手收入** | **¥7.5** | **¥15** | **¥30** |
| 月到手 | ¥225 | ¥450 | ¥900 |
| 发出能量 | 500 点/天 = 15,000 点/月 | 同 | 同 |
| 这些点的**零售价值** | ¥900–1,500 | 同 | 同 |
| 这些点的**评测成本** | 250 次挑战/天 ⇒ 🔶 ¥30/月 | 同 | 同 |
| **增量毛利（现金流口径）** | +¥195/月 | +¥420/月 | +¥870/月 |
| **机会成本（蚕食口径，假设 50% 本会付费）** | −¥600～900/月 | −¥450～750/月 | −¥150～450/月 |

⚠️ 参考口径校验：官方框架是 **ARPU = 变现利用率 × 人均曝光次数 × eCPM**。
按「DAU 1000、人均 3 次、填充 80%、到手 eCPM 30」也能算出日收入 ≈ ¥72 ——
但**我们的日上限只有 2–3 次且只在余额不足时才出现，人均曝光远达不到 3 次**
⇒ **上表 500 次/天（人均 0.5 次）比「人均 3 次」的乐观模型更接近我们的设计**。

⭐ 规模感结论：**DAU 1000 的广告月收入是「几十到几百元」量级，不是「几千元」**；
它**替代不了一次调价**（`ENERGY_PACKS` 改一档就是几十个百分点）。
⇒ 这条通道的**真实收益是「免费用户多一次挑战」带来的留存与转化**，钱是顺带的。**按这个定位去做，规则才定得对。**

## 5. 合规与风险清单

### 5.1 ✅ 结论：不违规（三条最接近的条款逐条核过）

原本最担心的一条 —— 「**开了虚拟支付还能不能做广告变现 / 看广告免费得点数算不算绕开虚拟支付**」——
查完官方原文的结论是：**没有任何条款禁止，且官方文档自证两者可并存**。

| # | 担心的点 | 官方原文与判定 |
|---|---|---|
| 1 | 开了虚拟支付就不能做广告变现？ | ✅ **无此条款**。《运营规范》**5.13** 原文：「开发者在小程序内提供的虚拟商品（包括虚拟代币、解锁功能、订阅内容、付费功能、打赏、购买虚拟礼物等），**购买和支付**均需接入小程序虚拟支付；不得引导至 app、公众号、h5、个人号、网站完成支付」⇒ 条文约束的是**付费通道**（钱必须走 xpay），**不是免费获取途径**。且虚拟支付文档内建「**广告金**」模块（平台赠广告金支持投放）⇒ **广告体系与虚拟支付是并存关系** |
| 2 | 「看广告免费得点数」算绕开虚拟支付吗？ | ✅ **不算**。**5.33** 打击的是引导用户去**线下充值/跳转其他小程序、APP、H5、公众号充值或购买** —— 同样只针对**付费**；小游戏规范 3.2「变相提供其它**支付方式**」亦属付费通道范畴。**免费送点与"支付方式"无关** |
| 3 | 算「诱导观看广告」吗？ | ✅ **不算**（前提是用户**主动点击**）。**5.34** 原文打击的是：「用户进入小程序后，使用正常功能服务过程中，小程序通过**自动弹出广告页面**等方式，诱导或强制用户观看点击广告，中断用户正常使用体验」⇒ 关键在**自动弹出 / 中断流程**，不在「给奖励」。⭐ 官方激励视频文档更直接写着：「大于等于 2.1.0 的基础库版本，开发者需要根据 `res.isEnded` 判断视频是否播放结束、**可以向用户下发奖励**」 ⇒ **「看广告 → 给奖励」就是官方设计的正向模型** |

⇒ ⭐ **方案本身合规，可以按 §4.5 去做。** 但仍建议**在开通虚拟支付时向客服复述一遍玩法并留档**
（官方口径会变、审核是人工的；一条工单换掉一个「事后被判定」的风险，很便宜）。
⭐ **降级方案**（若未来口径收紧）：广告奖励不给「能量」，改给**一次免费的评测机会/道具** ——
不增加可流通的货币余额，语义上更像「激励视频换一次服务」。

⚠️ **顺带一个和主体选择有关的重要发现（影响 plan.md A2，不属于本调研但必须说）**：
个人主体的虚拟支付文档明确写「**只做道具直购，不引入代币等额外功能**」，而我们卖的是**能量代币**
⇒ **个人主体这条路很可能装不下「能量」模型**（企业/事业单位/个体工商户那条没有这条限制）。
→ 详见 [../design/payment-and-purchase.md](../design/payment-and-purchase.md) §11.4，主体拍板前需要重新对照这一条。

### 5.2 原文红线清单（照这个写实现，不要凭印象）

**A. 《小程序流量主行为规范》v7.3.1（二级违规，可冻结权限 7/15/30/90 天并扣当月收入）**

| # | 官方原文 | 对我们的约束 |
|---|---|---|
| 1 | 「激励视频广告**未完全播放（提前关闭），流量主照常下发奖励**」 | ⇒ **必须** `onClose` 且 `res.isEnded === true` 才发 |
| 2 | 「激励视频广告**播放后未下发所承诺的奖励**」 | ⇒ 承诺 1 点就**必须**到账（服务端记账 + 幂等 + 失败重试），不能「看完没反应」 |
| 3 | 「**点击**激励视频广告后，**人为控制视频播放的时间**（包括但不限于延后播放）」 | ⇒ 不做「秒过」「后台播放」等任何花活 |

| 5 | 「**强制播放广告**：在用户使用过程中强制唤起激励视频广告进行播放」 | ⇒ 只做**用户主动点按钮**；不做启动即弹、不做流程卡点 |

| 7 | 「通过明示或暗示的方式**诱导、鼓励、煽动**用户反复访问、**点击**广告展示页面」 | ⇒ 文案不写「点广告」「必得大奖」 |

| 9 | 「**恶意作弊行为**：同一 IP 地址下重复点击或访问……制造虚假或无效曝光量、点击量」 | ⇒ 除单用户上限外，还要看 **IP/设备维度**的异常频次 |

**B. 《微信小程序平台运营规范》**

| 条款 | 原文要点 | 对我们的约束 |
|---|---|---|
| **5.34** | 通过**自动弹出广告页面**等方式，诱导或强制用户观看点击广告，**中断用户正常使用体验** | ⇒ 我的实现是「余额不足时出现一个可选按钮」，不自动弹 ⇒ **合规** |

| **3.11** | 对可能涉及不宜未成年人接触的内容或服务予以提醒或处理 | ⇒ 学习类用户里可能有学生，广告位不引导、不设卡点 |

⭐ **文案只写「观看完整视频可得 1 点能量」，不写「点击广告」**。

## 6. 建议的推进顺序（我的判断）

0. ✅ **合规这一关已经过了**（§5.1）：广告 + 虚拟支付并存、看广告免费发点，都没有禁止条款 ⇒
   **不需要先等一个"合规许可"再动手**；只要实现严守 §5.2 的原文红线即可。
1. ⭐ **先把小程序发出去**（不管广告还是虚拟支付，都要先上线）——**这是唯一的关键路径**。
   备案 → 上线 → 攒 UV；流量主只要 **UV ≥ 500** 就能开，**微信认证不是它的门槛**（认证是虚拟支付的）⇒ 广告通道可以比虚拟支付先跑起来。
2. **零门槛的免费能量先做**：签到 / 连战 / 每日任务发 1 点（`reward_rules` 已有触发器与发放接口，
   见 [../design/reward-system.md](../design/reward-system.md)）—— ⭐ **它今天就能开发、上线即可用，且没有 UV 门槛**。
   广告通道不是「免费能量的第一来源」，是**破 500 UV 之后的第二来源**。
3. 破 500 UV、开流量主后：按 §4.5 的规则做**1 点/次、日上限 3 次、只在余额<2 时给入口**的最小版本（≈3 人日），
   并**同时问微信广告客服：小程序能不能用 SSV**（§3.3）—— 这一问决定要不要多做 1 人日的验签回调。
4. 上线第一周就去后台拿 **7 天真实数据**：① 确认 eCPM 仍是**到手口径**；② 用我们的真实 eCPM
   （以及拉取→曝光的填充率）**替换掉 §4.2 的 10–60 经验区间**，再决定要不要调整发放点数。
5. 之后每 4 周看三个数：**广告完成率 / 领广告能量人群的次日留存 / 付费转化率是否下降**。
   ⚠️ 第三个数是**刹车指标**：若付费转化明显下滑，先降到「每人每天 1 次」再评估。
6. 反向验证（很重要）：跑一次「不给广告」的对照组，确认留存提升真的来自广告而不是季节性。
