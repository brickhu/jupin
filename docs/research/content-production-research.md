# 内容生产调研

> 素材库（竞技场）生产流程所需的三个外部依赖：TTS + 词级时间戳、词典数据、朗读难度定级。

---

## 一、TTS 与词级时间戳 —— fish-audio ✅

**结论：fish-audio 原生支持词级时间戳，正好是素材库最需要的东西。**

接口：POST /v1/tts/stream/with-timestamp

```json
{
  "content": "Hello world",
  "chunk_seq": 0,
  "chunk_audio_offset_sec": 0.0,
  "alignment": {
    "audio_duration": 0.86,
    "segments": [
      { "text": "Hello", "start": 0,    "end": 0.42 },
      { "text": "world", "start": 0.42, "end": 0.86 }
    ]
  }
}
```

**segments 就是词级时间戳**，官方文档自己的用途说明是「karaoke-style highlighting, word or phrase progress indicators」。

**一个接口同时解决两件事**：标准发音音频 + 每个词在音频里的位置。

### ⭐ 为什么时间戳是硬需求

「逐词 A/B 对比」需要**双方都有词级时间戳**：

| 音频 | 时间戳来源 | 状态 |
|---|---|---|
| 标准发音 | fish-audio alignment.segments | ✅ |
| 用户录音 | 云端评分结果（讯飞 beg_pos/end_pos，单位 10ms） | ✅ |

**不存时间戳，点词功能就是错的。**

### ⚠️ 音频策略

**整篇 + 每个竞技场各生成一份。**

理由：用户实际是**独立读一个句群**的，竞技场标准音也应独立生成——**韵律条件一致，A/B 对比才公平**。TTS 成本可忽略。

### ⚠️ 最容易踩的坑：分词对齐校验

fish-audio 返回的 segments[].text 是它自己切的词，必须与自建词表**逐项一致**，否则时间戳对不上。

常见差异：缩写（don't vs do + n't）、标点（dress, vs dress）、连字符、数字。

**必须做严格校验：**

```
比对 segments.length === words.length
且逐项比对 text（去标点、统一小写后）
不匹配 → 标记出来人工修正或重新合成
```

**而且切词规则须与评分引擎一致**（讯飞有明确的官方分词分句规则，见 ise-probe-report.md）。

## 二、词典数据 —— ECDICT ✅

**结论：一个 MIT 协议的开源英汉词典，同时覆盖音标 + 词性 + 义项 + 词形变化 + 难度标签。**

skywind3000/ECDICT — **MIT 协议（可商用）**，约 **76 万词条**，有 npm 包与 SQLite 版本（建议转 SQLite，查询远快于读 CSV）。

| 字段 | 内容 | 用途 |
|---|---|---|
| phonetic | **音标** | ⭐ 音标（**绝不能让 LLM 生成**） |
| pos | **词性**（/ 分隔多词性） | 词级数据 |
| translation | **中文释义**（全部义项） | 词级数据 |
| definition | 英文释义 | 可选展示 |
| exchange | **词形变化** | 词典查找还原 |
| tag | **考试标签**（zk/gk/cet4/cet6/ky/toefl/ielts/gre） | ⭐ 难度定级参考 |
| collins / oxford | 柯林斯星级 / 牛津核心词 | 难度参考 |
| bnc / frq | 语料库词频 | 难度参考 |
| lemma | 原型 | 词形还原 |

### ✅ 2026-09 实施：字典做成 LLM 的 tool-call（`dict_lookup`）

**不是「代码先算好难度再喂模型」，而是把 ECDICT 本身交给模型当工具**（用户 2026-09 的决定）。
落地方式：

- `tools/build-ecdict-index.ts`（`pnpm content:ecdict`）把 ECDICT 的 CSV 转成一份扁平索引
  `.cache/ecdict.json`：**77 万词条 + 5.96 万条屈折形→原形映射**（约 23MB，已 gitignore，可重建）；
  用 pnpm 装的 `ecdict` 包里的 assets，RFC4180 解析（词条里有引号与逗号）。
- `tools/pipeline/src/lib/ecdict.ts` 暴露 `dict_lookup`：查一个词，返回
  `{ word, lemma, phonetic, tag, collins, oxford, bnc, frq }` —— **只给原始字段，不给档位结论**。
- `llm.ts` 的 `chatJsonWithTools` 跑一个标准的 OpenAI 兼容 tool loop
  （前几轮带 tools，最后一轮去掉并强制 `response_format: json_object`）；
  工具报错**回给模型**而不是抛出去 —— 模型可以换个词再查。

**为什么不下放到代码里算**（实测出来的三个坑，任一个都会造成静默的错档位）：

| 坑 | 例子 | 后果 |
|---|---|---|
| 高级词表也收基础词 | `as` 带 ielts、`way` 带 toefl | 取最高 tag → 把小学词判成六级词 |
| 屈折形常常没填 tag / 词频 | days、sells、shells、frowns | 不还原原形 → 把基础词判成超纲 |
| 个别字段是坏的 | `is` 的 bnc=24648 | 拿它下结论 → 一个没人会发现的错档位 |

⇒ 代码只保证「**数据查得到、查得对**」（含 lemma 优先的还原顺序），
「这个 tag 和一个 bnc=73 的词频打架时该信谁」留给模型 —— 这正是 tool-call 的意义。

> ⚠️ **2026-09 实测修正**：往前一步试过「让模型跟着 tag/词频定档」（tag 取最低档 + 词频兜底 +
> 常用度优先），**比模型自己的词汇判断更不准** —— 词表的高档位噪声太大（shells→gre、
> seashore→toefl），而词频高低与「中文学习者觉得难不难」也不等价。
> 最终口径：**逐词定档以模型判断为准**，`dict_lookup` 只用于核实拿不准/疑似超纲的词。
> 复核手段是把用户给的 6 句锚点整批过一遍真实流水线，看最终档位是否命中（见 spec.md 第九节）。

### ⭐ 关键设计：让 LLM 从「生成」降级为「选择」

```
❌ 原来：LLM 输入句子 + 单词 → 输出音标 + 词性 + 释义   （从零生成，会编）
✅ 修正：ECDICT 查出音标 / 词性 / 全部义项
        → LLM 只回答「在这句话里哪个义项对，用 5–15 字精简」
```

| | 从零生成 | 从义项里选 |
|---|---|---|
| 幻觉风险 | **高** | **低**（有权威依据） |
| 音标 | 可能错且难发现 | **不用 LLM，直接查表** |
| 成本 | 每次生成 | 输出更短，更便宜 |

**⚠️ LLM 生成的音标会幻觉，而且你很难发现。音标必须查词典。**

## 三、朗读难度定级

### ⚠️ 核心区分：「朗读难度」≠「阅读难度」

| 维度 | 阅读难度 | **朗读难度** |
|---|---|---|
| 词汇生僻 | ✅ 主要 | ⚠️ 次要 |
| 句法复杂 | ✅ 主要 | ⚠️ 次要 |
| **语音难点密度** | ❌ 无关 | ✅ **主要** |
| **连读/弱读密度** | ❌ 无关 | ✅ **主要** |
| **长度/气息** | ⚠️ | ✅ 主要 |

**极端例子：**

> "The sixth sick sheikh's sixth sheep is sick."
> 所有单词都是高考及以下词汇 → 按词汇算难度是 ⭐
> **但这是公认的英语最难绕口令**（/s/ /ʃ/ /θ/ 在 8 个词里反复切换）→ 真实朗读难度 **⭐⭐⭐⭐⭐**

**若按词汇定级，绕口令会被标成最简单的一档 → 「征服 ⭐」失去含金量 → 整个征服体系崩塌。**

### 方案：脚本算特征 → LLM 综合判断 → 人工审核

> ⚠️ **2026-09 已废弃上面这条「脚本算特征」的路** —— 难度改为**全由 LLM 判**（见 spec.md 第九节）。
> 下面这张特征表**保留为调研记录**（它说清了难点在哪），但流水线不实现它，别照着做。

**喂给 LLM 的客观特征**（脚本计算）：

| 特征 | 说明 |
|---|---|
| **难音密度** | 含 /θ/ /ð/ /v/ /w/ /l/ /r/ 及长短元音对立的词占比 ⭐ 最强预测因子 |
| **连读点数量** | 词尾辅音 + 下词首元音 |
| **弱读功能词数量** | 中国学习者的主要失分点 |
| 词数 / 音节数 | 气息和长度 |
| 最长词音节数 | 单词本身难度 |
| 句法复杂度 | 次要 |
| ECDICT 词汇难度 | 次要 |

**⭐ 锚点是关键**：必须提供 **5–10 条人工已定级样本**作为参照，覆盖 ⭐ 到 ⭐⭐⭐⭐⭐。
**没有锚点，LLM 的星级标准会漂移**（同一句今天 ⭐⭐⭐、明天 ⭐⭐）。

> ✅ 2026-09：锚点**已采用** —— 而且是被实测逼出来的：
> 只给四档文字描述时，重判 8 句有 **7 句上移、5 句挤在「高级」**；
> 加上**每档一句参照样本**后，分布才散开（当时 8 句：初级 1 / 中级 2 / 高级 3 / 专家 2）。
> 上面这条结论**被实测证实了**。样本见 tools/pipeline/src/lib/article-meta.ts 的 SYSTEM。

### 现成的句子难度定义方法调研（2026-09）

用户问「其实有很多现成定义句子难度的方法」—— 确实有，分四类，只有第二类站得住：

| 类别 | 代表 | 用不用 |
|---|---|---|
| **可读性公式** | Flesch Reading Ease、Flesch-Kincaid Grade、Gunning Fog、SMOG、Coleman-Liau、ARI、Dale-Chall | ❌ 见下 |
| **词表 / 覆盖率分档** | Nation 的 word family 分档与 95% / 98% 覆盖率、CEFR 词表（Oxford 3000/5000、CEFR-J、NGSL/SVL）、ECDICT 的 `tag` | ⭐ **采用**（作为词汇判据的数据） |
| **句法复杂度指标** | 从句数、依存树深度、平均句长（L2 Syntactic Complexity Analyzer） | ⭕ 并入「词汇及句式」这一维 |
| **语言模型打分** | CEFR 分类器、perplexity、可读性回归模型 | ⭕ 本项目现在就是 LLM 在判 |

**可读性公式为什么不能用**：
1. 它们是给**整篇文章**设计的 —— 对 10–20 词的单句，音节数与句长的方差极小，
   算出来全挤在中段，分不出我们要的四档；
2. 它们量的是**母语者的阅读难度**，不是「中文母语者念出来有多难」—— 发音难点它一个都不看；
3. 校准样本是 L1 学生（美国年级），与我们的用户群（中国英语学习者）不同源。

**发音难度没有现成公式**：调研过 phonotactic difficulty、functional load、sonority sequencing、
L1 迁移易错音清单 —— 它们给的是**成分**，不是可算的分；
而最强的难点（音素切换模式，即绕口令）恰恰不落在任何单一指标上。
⇒ 这一维只能由 **LLM 按锚点判**，这也是「锚点是关键」那条结论的由来。

### ✅ 2026-09 最终采用的难度模型（覆盖上面的方案）

**一个对外档位 + 三个内部判据**，判据各 1–5 分、加权合成：

| 判据 | 权重 | 数据来源 |
|---|---|---|
| 词汇及句式 | 5 | **ECDICT 作为 LLM 的 tool-call（dict_lookup）**：模型拿不准就查，工具给原始字段 |
| 发音 | 4 | LLM 按 5 档锚点判（下面「必须抽查的两类易错」那两条就是它的边界） |
| 句子长度 | 1 | 数词 |

`score = (5×词汇 + 4×发音 + 1×长度) / 10`，落在 1–5；档位 = **四舍五入到整数**：1–2 初级 / 3 中级 / 4 高级 / 5 专家（切分点 2.5 / 3.5 / 4.5）。
公式与权重在 `packages/shared/src/level.ts`；**算术由代码做**（模型只给三个分）。
三个分记进正文 JSON（`scores`）**只是为了能被代码验算**，不对用户展示。

**为什么不用可读性公式**（Flesch / Flesch-Kincaid / Fog / SMOG / Coleman-Liau / ARI / Dale-Chall，
见上一节）：它们是为**整篇文章 + 母语者阅读**设计的，对 10–20 词的单句方差极小、
区分不出四档，而且量的不是「中文母语者念出来有多难」。
站得住的是 **Nation 式词表分档** —— 而 ECDICT 的 `tag` 正好是
zk / gk / cet4 / cet6 / ky / toefl / ielts / gre，几乎 1:1 对上我们的五档。
⚠️ 但**不能让代码直接用它下档位结论**（实测的坑）：取最高 tag 会把 `as` / `way` 判成六级词；
屈折形常常没填 tag；`is` 的 bnc 是坏的 —— 所以只把**原始字段**给模型。

**稳定性措施**：temperature 设 0–0.2 · 定级一次即固化入库 · 人工审核后锁定。
**输出要求**：stars + **reason**（可解释，人工审核时一眼能判断对错）。

### 必须抽查的两类易错

| 易错类型 | 例子 |
|---|---|
| 词汇难但朗读不难 | "The utilization of sophisticated methodologies…" → 别被长词骗 |
| ⭐ **词汇简单但朗读极难** | 绕口令 → **最容易漏判，且漏判是致命的** |

## 四、朗读技巧生成

### ⚠️ 不能让 LLM 自由发挥

LLM 的语音学判断不可靠：会编造不存在的连读、漏掉真正的难点、拼错音标。**而技巧是用户会照着练的东西——错了就是教错。**

### 正解：规则检测 → LLM 润色 → 人工审核

**第一步：规则检测**（脚本，零成本，精确）

| 技巧类型 | 检测规则 | 数据来源 |
|---|---|---|
| **连读** | 词尾是辅音 + 下一词首是元音 | 音标（ECDICT） |
| **弱读** | 匹配固定功能词表（a/an/the/at/to/for/of/and…） | 词表 |
| **难音** | 音标含 /θ/ /ð/ /v/ /w/ /l/ /r/ /iː/ /ɪ/ /uː/ /ʊ/ | 音标（ECDICT） |
| **词尾辅音** | 词尾辅音后无元音，且是多音节词 | 音标 |
| **重音** | 3 音节以上的词 | 音标 |
| **语调** | 句末标点（. 降调，? 升调） | 文本 |

**这些都是确定性规则，不会编。**

**第二步：LLM 只做润色**——挑 1–3 条最值得说的，用自然中文写出（每条 20–40 字），**约束：只能针对已检测出的点，不得新增**。

**第三步：人工审核**（内容量小，可行；前 50 句建议 100% 过一遍）。

### ⭐ 技巧应配示范音频

用词级时间戳精确切出对应短语的音频：

```
① looked at 连读，读成 /lʊktət/        [▶ 听这句]
② the / to / of 要弱读，别读太重        [▶ 听这句]
```

**「听短语的标准读法」比「看音标」有用得多**——大部分中文用户看不懂 IPA，**文字 + 示范音频是主体，音标只是辅助**。

### ⭐ 技巧不该是静态展示

**真正的用武之地是重录循环里的兜底：**

```
预检失败 → "girl 这个词没听清，再读一遍试试"
        → 💡 girl 的 /ɜːr/ 要卷舌到位  [▶ 听示范]
        → [ 重录 ]
```

**用户不会主动去读技巧，但他在卡住的那一刻一定会看。**
