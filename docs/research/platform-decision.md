# 平台选型论证：小程序 vs 原生客户端

> 结论：**做微信小程序。**

---

## 一、判断框架

区分两类差距——这个框架决定了结论：

| 类型 | 能否用工程量弥补 | 举例 |
|---|---|---|
| **实现便利** | ✅ 能 | 手写 FFT、音频精确切片、逐词时间戳 |
| **能力缺失** | ❌ 不能 | 传播效率、下载门槛 |

**用工程量能换来的东西，不值得用传播链路去换。**

---

## 二、端侧能力逐项核对

按「云端只买一个分数」原则，端侧必须做到这些：

| 端侧能力 | 小程序能做吗 | 说明 |
|---|---|---|
| 录音（PCM 16k 单声道） | ✅ 能 | getRecorderManager + onFrameRecorded |
| 本地预检（VAD/能量/时长） | ✅ 能 | 纯 JS 信号处理 |
| ASR 可识别性预检 | ✅ 能 | 微信同声传译插件（免费） |
| 实时进度 | ✅ 能 | 插件 onRecognize |
| **音高曲线** | ⚠️ **能，但要手写 FFT** | 小程序无 AnalyserNode |
| 语速 / 停顿 / 流利度 | ✅ 能 | 纯算法 |
| 点词回放 / A/B 对比 | ⚠️ **能，但要变通** | 用**预切音频**规避 seek() 精度问题 |
| 逐词上色（DTW） | ✅ 能 | 纯 JS 算法 |
| 全部 UI / 动画 | ✅ 能 | — |
| **端侧音素级模型** | ❌ **不能** | createInferenceSession 为 Beta + 算子受限 |

**结论：端侧必需能力，小程序全都能做。** 只有两项是「实现便利」问题。

**而端侧模型那一项，本来就放在 P2**——它是锦上添花，不是核心循环。

---

## 三、⭐ 决定性因素：竞技场需要人口，人口需要传播

**竞技场的价值 = 榜单密度 = 参与人数。** 而参与人数取决于从「看到」到「玩上」的转化率：

| | 小程序 | 原生 App |
|---|---|---|
| 分享到群 | 卡片 → **点开就玩** | 链接 → 跳浏览器 → 引导下载 → 装 App → 注册 → 玩 |
| 漏斗 | **~90%** | **~10%** |
| 首次体验 | 秒开 | 下载 100MB+ |

**对一个「以句子为单位打造竞技场」的产品，传播链路就是生命线。**
**App 的下载门槛会直接掐死榜单密度——而榜单稀疏的竞技场，是没有存在意义的。**

**这是「能力缺失」级别的差距，不是工程量能补的。**

---

## 四、支持 App 的论证（诚实列出）

| App 的优势 | 严重度 |
|---|---|
| iOS 的 SFSpeechRecognizer 免费给**逐词时间戳** | 省掉自己算词边界 |
| iOS 的 SFVoiceAnalytics 免费给**逐词音高/抖动/闪烁** | 省掉手写 FFT |
| SpeechAnalyzer（iOS 26）模型在**系统空间，零体积** | 省掉模型分发 |
| Core ML / NNAPI：**端侧模型可行** | 真·零边际成本 |
| 音频控制精确（AVAudioPlayer） | 省掉小程序那些变通 |

**但这些全是「实现便利」，不是「能力缺失」：**

- 手写 FFT 约 320 行代码
- 词级时间戳可从云端打分结果拿（或本地 DTW）
- 端侧模型是 P2

---

## 五、小程序的代价（诚实版）

| 代价 | 应对 |
|---|---|
| 手写 FFT 做音高分析 | 一次性工程量，约 1–2 天 |
| 音频精确切片播放需变通 | 用**预切音频文件**规避 |
| 主包 2MB | 资源全在 CDN，无压力 |
| **类目/资质审核** | 报「**工具**」而非「教育」——既避资质门槛，又能开虚拟支付 |
| 微信政策变更风险（如同声传译插件） | ⭐ **用「引擎无关」原则隔离** |

### ⭐ 风险隔离

对微信能力的依赖只有两处，且都有兜底：

| 依赖 | 兜底方案 |
|---|---|
| 同声传译插件（ASR 预检 + 实时进度） | 退回**纯本地时长/能量判断**（精度略降，功能不丢）；或改用 fish-audio ASR |
| 支付 | 小程序虚拟支付 |

**插件就算变了，产品也能跑，只是体验降一档。这不是致命依赖。**

---

## 六、结论

> **做小程序。**

**三条理由，按权重排序：**

1. **竞技场需要人口密度，人口密度需要传播效率——这一条 App 结构性做不到**
2. **端侧必需能力小程序全都能实现**，只有两项是工程量问题
3. **端侧模型（App 唯一的独有优势）本来就是 P2**，不影响当前决策

---

## 七、什么条件下该转 App

| 触发条件 | 说明 |
|---|---|
| **数据显示用户流失主因是「反馈不够精确/不够实时」** | 而不是「不知道这个产品」 |
| **端侧音素级诊断成为核心差异化** | 竞品都在做，而小程序做不了 |
| **已有足够用户量支撑下载转化** | 例如 DAU 过万，且有自然搜索流量 |

**而且因为架构是「云端只要一个分数」，转 App 的成本主要在 UI 重写，不在能力重建——这个决定是可逆的。**
