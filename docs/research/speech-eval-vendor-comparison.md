**能力（✅ 官方）**

## 3. 小程序平台的硬约束（跨厂商通用）

这些约束**与选谁无关**，但会决定架构。完整证据见项目内 [微信小程序「录音 + 上传音频到第三方服务」合规调研](../微信小程序-录音上传第三方-合规调研.md)。

| 约束 | 内容 | 对选型的影响 |
|---|---|---|
| **服务器域名白名单** | `wx.request` / `wx.uploadFile` / `wss` **只能连已配置域名**；仅 https/wss；禁 IP / localhost；**域名必须 ICP 备案** | ⚠️ **Azure（azure.com / azure.cn）配不进去**；讯飞、有道、SOE 的域名也都不在你的白名单里 → **必须自建备案域名中转**。这不是优化项，是硬约束 |
| **并发上限** | request / uploadFile / downloadFile 各 10 个；socket 5 个 | 影响「预取下一句音频」等设计的余量 |
| **隐私协议** | 录音的隐私类型为「访问你的麦克风」；**未在指引中声明即直接禁用**（errno 112） | 所有走录音的方案都一样，不构成厂商差异 |
| **录音授权** | `scope.record`；**已拒绝后不再弹窗**，必须兼容引导 | 同上 |
| **生物识别** | 运营规范 15.3.10：涉及**声纹识别**应使用微信平台提供或认可的技术 | ⚠️ 「收集用户声纹」的产品化包装有合规风险，所有厂商一视同仁 |

⚠️ **一个常见误解**：小程序插件主页上的「类目」是**插件自身**的服务类目，**官方并无「插件类目必须与小程序类目匹配」的规定**（[微信官方 使用插件](https://developers.weixin.qq.com/miniprogram/dev/framework/plugin/using.html) 全文无此要求）。

## 4. 端侧纯离线方案（不建议作为主评分链路）

> 详细证据见 [vendor-ondevice-landscape.md](vendor-ondevice-landscape.md)。

**技术路线**：声学模型后验 → **GOP（Goodness of Pronunciation）**。Kaldi 官方 recipe 明确：分类器方法优于纯 GOP，且**chain 模型不适合算 GOP**（需 nnet3 非 chain TDNN）→ **依赖强制对齐 + 声学模型后验**，这是端侧的核心成本。

**已证实的打分相关性**（这是决定性的数字）：

| 方案 | 粒度 | 相关性 |
|---|---|---|
| Kaldi 官方基线（speechocean762） | 音素级 原始 GOP | MSE 0.69 / **PCC 0.25** |
| Kaldi 官方基线 | 音素级 GOP 特征 | MSE 0.16 / **PCC 0.45** |
| GOPT（ICASSP 2022） | 音素级 | RF 0.44 / SVR 0.45 / **LSTM 0.591** |
| GOPT | 句级 | 前人最好 **0.720** |
| OpenPronounce | 句级（500 句） | **Pearson 0.633 / Spearman 0.652** |

**平台可行性**（✅ 官方）
- **WXWebAssembly 存在**：v2.13.0 起全局可用，v2.15.0 起可在 Worker 内使用；支持 Memory / Table / Global；**文档未承诺多线程 / SharedArrayBuffer / SIMD**。
- ⭐ 微信另有原生端侧推理 API **`wx.createInferenceSession`（ONNX，AI 推理能力 Beta）**，比自建 WASM 更现实（自带量化支持）；但**算子覆盖、模型体积上限、端侧耗时必须实测**（文档页 JS 渲染，未能抓取明细）。
- 体积：Wav2Vec2 权重 **~1.2GB/个**（官方），远超小程序代码包量级，须蒸馏 / 量化到数十 MB。

**结论**：
- ✅ **可以做**：朗读跟读的**即时反馈**（漏读、明显错音）、**录音质量预检**、断网降级。
- ❌ **不能做**：正式评分、排名、付费判定 —— 句级相关仅 **r≈0.6**，且跨设备不可复现、不可仲裁。
- ⚠️ **没有任何开源仓库声明支持端侧推理**，端侧化需自行导出量化；工作量 🔶 1–2 人月原型起步（估算，无官方来源）。
- 中文开源尤其薄弱（std-mandarin-kaldi 仅 8★、2021 后无更新）→ **中文需自建**。

## 5.3 如果将来仍要用腾讯云 SOE —— 后端要做什么（✅ 官方 demo 实证）

腾讯官方小程序/小游戏 demo 仓库 [TencentCloud/tencentcloud-demo-mp-soe](https://github.com/TencentCloud/tencentcloud-demo-mp-soe)（最近提交 2025-07-23）给出了生产路径的最小实现 —— **服务端用 STS 换联合身份临时凭证**：

```js
// node-demo/authorization.js（官方原文）
const StsClient = tencentcloud.sts.v20180813.Client;
const policy = {
  version: '2.0',
  statement: { effect: 'allow', action: ['soe:TransmitOralProcessWithInit'], resource: '*' }
};
const res = await client.GetFederationToken({ Name: 'soe', Policy: encodeURIComponent(JSON.stringify(policy)) });
```

客户端：

```js
let manager = plugin.getSoeRecorderManager({
  getAuthorization: function (callback) {
    wx.request({ url: 'https://example.com/server/getFederationToken', method: 'POST', success: data =>
      callback({ TmpSecretId: data.TmpSecretId, TmpSecretKey: data.TmpSecretKey, Token: data.Token }) })
  }
});
```

⭐ **这就是「插件不免后端」的具体形态**：你仍然要写一个服务端接口 + 腾讯云 STS 权限策略 + 自己的鉴权层（官方 README 明确提醒「正式部署时请在后台加一层自己网站本身的权限检验」）。
