# 微信小程序 API 约束（官方文档核实）

> 本文记录**从官方文档核实到的硬约束**，以及它们对句说设计的影响。
> ⚠️ 这些是"不查文档就会踩、踩了很难查"的东西——类似腾讯云 SDK 那次误判。

---

## 一、RecorderManager.start —— 完整参数（官方）

| 属性 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `duration` | number | 60000 | 录音时长 ms，**最大 600000（10 分钟）** |
| `sampleRate` | number | 8000 | ⚠️ **pc 不支持**。合法值 8000/11025/12000/16000/22050/24000/32000/44100/48000 |
| `numberOfChannels` | number | **2** | ⚠️ **默认是双声道**。1 或 2 |
| `encodeBitRate` | number | 48000 | 有效值见下方对应表 |
| `format` | string | **aac** | mp3 / aac / wav / **PCM** |
| `frameSize` | number | — | **指定帧大小，单位 KB**。传入后每录制指定帧大小回调一次。⚠️ **暂仅支持 mp3、pcm 格式** |
| `audioSource` | string | auto | 音频输入源，见 `wx.getAvailableAudioSources()` |

### ⭐ 采样率与编码码率的对应关系（设错会直接录音失败）

| 采样率 | 编码码率有效范围 |
|---|---|
| 8000 | 16000 ~ 48000 |
| 12000 | 24000 ~ 64000 |
| **16000** | **24000 ~ 96000** |
| 22050 | 32000 ~ 128000 |
| 24000 | 32000 ~ 128000 |
| 32000 | 48000 ~ 192000 |
| 44100 | 64000 ~ 320000 |
| 48000 | 64000 ~ 320000 |

**我们用 16000Hz → encodeBitRate 必须落在 24000~96000，选 48000。**

### ⚠️ 我们代码里踩到 / 差点踩到的三个坑

| # | 坑 | 后果 | 状态 |
|---|---|---|---|
| **1** | `frameSize` 单位是 **KB 且必须是整数** | 传 `1280/1024 = 1.25` 可能无效 | ✅ 已改为 **2**（整数 KB） |
| **2** | `numberOfChannels` **默认 2** | 不显式传 1 会拿到立体声，与引擎「单声道」要求不符 | ✅ 已显式传 1 |
| **3** | `sampleRate` **PC 不支持** | 开发者工具里此参数无效 → **必须真机验证** | ⚠️ 记入验证清单 |

### ⭐ frameSize 的选择权衡

- **1 KB** = 1024 字节 = 512 采样 = 32ms
  - 进度追踪更细，但 **YIN 基频检测在 70Hz 下限需要 ≥2 个周期（≈457 采样），512 太勉强**
- **2 KB** = 2048 字节 = 1024 采样 = 64ms ← **我们选这个**
  - 基频检测可靠，VAD 与进度追踪仍够细

## 二、Worker 的硬限制（官方）

| 约束 | 说明 |
|---|---|
| **最大并发 1 个** | ⚠️ 创建下一个前**必须** `Worker.terminate()` 结束当前 Worker |
| **只能 require Worker 目录内的文件** | ⚠️ 无法引用其它路径 |
| **不支持 wx 系列 API** | Worker 在独立全局上下文 |
| 入口由 `wx.createWorker()` 动态指定 | — |
| Workers 之间不支持通信 | — |
| **数据传输是「复制」而非共享** | postMessage 有拷贝开销 |
| 全局暴露 `worker` 对象 | `worker.onMessage` / `worker.postMessage` |
| `app.json` 配置 | `{ "workers": "workers" }`，该目录下代码**会被打包成一个文件** |

### ⭐ 对架构的决定性影响

**「只能 require Worker 目录内的文件」+「目录下代码打包成一个文件」= 用 esbuild 把 shared 打进去是唯一可行方案。**

我们不是"选择"了 esbuild 打包，而是**只能这么做**——否则 Worker 里 require 不到 `@jushuo/shared`。

⚠️ 另外：因为**最大并发 1 个**，Worker 的创建/销毁必须是严格的串行状态机。我们当前的"自检时 createWorker → onMessage → terminate"模式是对的，但**如果忘记 terminate，下一次创建会失败**。

## 三、包体积限制（官方）

| 项 | 限制 |
|---|---|
| **整个小程序所有分包** | **不超过 20M** |
| **单个分包 / 主包** | **不超过 2M** |
| 分包数量 | 最多 20 个（常规） |
| 插件代码 | **不计入分包大小** |

其他可用特性：**分包异步化**、**独立分包**（不依赖主包单独运行）。

### 对句说的影响

我们的资源（标准音音频、词级数据）**全部走 CDN**，不进包——所以 2M 主包限制对我们几乎无压力。

**待验证**：esbuild bundle 后的实际体积（把 `@jushuo/shared` 打进去后）。当前 Worker 单文件只有 6.6KB，很宽裕。

## 四、对验证实验的影响

这次查文档**新增/明确了三条必须真机验证的项**：

| # | 验证项 | 为什么 |
|---|---|---|
| **1** | `onFrameRecorded` 在 iOS / Android 是否都稳定回帧 | 它挂了整个端侧分析不可用 |
| **2** | `sampleRate: 16000` 是否真的生效（PC 不支持，真机才准） | 采样率错了音频就是错的 |
| **3** | 实际 `frameBuffer.byteLength` 是否等于 `frameSize × 1024` | 决定分帧假设是否成立 |
| **4** | `numberOfChannels: 1` 是否真的拿到单声道 | 否则要降混，且引擎会判格式不符 |

**这四项都能在一次真机自检里测出来。**
