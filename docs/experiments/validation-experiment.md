### 结论一：端侧架构成立 ✅

决策树里那条「T1 不回帧 → 端侧分析不可行 → 改为录音上传云端分析」的分支**不用走了**。
「高频动作边际成本为 0」这条设计原则保住了。

### 结论二：`frameSize` 只是建议，不是契约 ⚠️

```
请求 2KB（2048 字节）
  → iOS     实际 4096 字节（1024 采样 → 2048 采样 = 128ms）
  → Android 实际 2560 字节（1280 采样 = 80ms）
```

**两端都不采纳，且给出的值互不相同**（Android 的 2560 = 2.5KB 不是 2 的幂，显然是内部缓冲决定的）。

⇒ **绝不能拿它推期望值**。第一版自检把「帧应为 2048 字节 / 间隔应为 64ms」写死，
于是把上面这份**完全正常**的数据误判成两项失败。现在判定改为验**自洽性**
（帧字节数 ÷ 实测字节率 ≈ 帧间隔），并已固化成回归测试。

⇒ Worker 侧用 `AUDIO_SPEC.frameSamples` 重新切帧，与录音帧大小**解耦**，功能上不受影响。

### 结论三：iOS 的 JS 执行比 Android 慢一个数量级 ⚠️

同样是 YIN 单帧检测：**iOS 7.2ms vs Android 0.55ms，差 13 倍**。
Redmi K30（2019 中端机）不该快过 iPhone 15，所以这不是硬件差距。

**待验证的假设**：iOS 上第三方 App 的 JavaScriptCore **没有 JIT**
（iOS 只给 WebKit 开 JIT 权限），小程序的 Worker 跑在解释模式；
Android 小程序用 V8，有 JIT。

为此在自检里加了**纯算术微基准**（`microbench` 消息）：跑 SMI 范围内的整数循环，
有 JIT 会被编译成机器码，纯解释则慢一个数量级。Node（V8 + JIT）参照值约 **333,000 ops/ms**。
下一轮真机自检会把三端数字并排报出来，假设成立与否一目了然。

**为什么现在不优化**：7.2ms / 64ms = 11% CPU，离瓶颈很远。
但**将来若要在每帧上跑更多算法（共振峰、DTW 对齐），必须按 iOS 的数字做预算**。
真要优化时的首选手段是**基频检测前先降采样**（只需要 70–400Hz，4kHz 采样足够，
样本数与 tau 范围同时缩小，理论上有 10× 以上的收益）。

> ⚠️ **对产品的直接影响**：端侧算法的性能预算必须按 **iOS 的数字**定，
> 不能拿 Android 或桌面浏览器当参照。
