# 合并验证实验方案

> **动手前的必经步骤。** 一次采集，同时回答 6 个问题，成本低于 ¥100。
> 这些问题**全部靠数据、不靠讨论**。

---

## 一、要回答的问题

### 产品侧（4 个）

| # | 问题 | 影响 |
|---|---|---|
| **P1** | **朗读难度是否真的影响拿分难度** | ⭐ **决定「统一 85 分阈值」成不成立** |
| **P2** | 真实分数分布 → **阈值标定** | 决定征服体系的成就感 |
| **P3** | ASR 对**重口音英语**的识别率 | 决定本地预检第③层会不会误伤 |
| **P4** | **竞技场切分长度与重录意愿** | 决定 10–20 秒是否最优 |

### 技术侧（2 个）

| # | 问题 | 影响 |
|---|---|---|
| **T1** | onFrameRecorded 在 iOS/Android 的真机行为 | ⚠️ **最高风险**——它挂了整个端侧架构要重来 |
| **T2** | 手写 FFT/自相关在 Worker 中的性能 | 决定音高曲线是否可行 |

> ⚠️ **开发者工具无法调试麦克风，T1/T2 必须真机。**

## 二、材料准备

### 语音样本

**选 5 个竞技场，覆盖 5 个星级**，每段 10–20 秒（25–50 词）。

⭐ **必须包含一个"词汇简单但朗读极难"的样本**（例如绕口令），这是 P1 的关键测试点：

| 星级 | 样本类型 |
|---|---|
| ⭐ | 短名言（4–13 词扩展版） |
| ⭐⭐ | 日常短句 |
| ⭐⭐⭐ | 中等句式 |
| ⭐⭐⭐⭐ | 复杂从句 |
| ⭐⭐⭐⭐⭐ | ⭐ **绕口令**（如 "The sixth sick sheikh's sixth sheep is sick."） |

### 朗读者

**4–6 人，覆盖不同发音水平**（这是 P1 和 P3 的关键）：

| 类型 | 人数 | 用途 |
|---|---|---|
| 发音较好 | 1–2 | 上界参考 |
| 中等（典型目标用户） | 2 | 主要样本 |
| **发音较差 / 重口音** | 1–2 | ⭐ **P3 的关键样本** |

### 录音规范

- **16k / 16bit / 单声道 PCM**
- 安静环境、固定麦克风距离
- 每段**录 3 遍**（第 1 遍自然读、第 2/3 遍允许重录）

## 三、执行步骤

```
Step 1  用 fish-audio 生成 5 个竞技场的标准音（含词级时间戳）
Step 2  每个朗读者 × 每个竞技场 × 3 遍 = 每人 15 条录音
        4 人 → 60 条；6 人 → 90 条
Step 3  全部送讯飞 ISE 评测（⚠️ 记得 ise_unite=1）
Step 4  全部送 ASR（微信同声传译插件 / fish-audio），记录识别词数
Step 5  跑真机技术验证（T1/T2）
Step 6  汇总分析
```

**成本估算**：60–90 次评测 × ¥0.00387 ≈ **¥0.35**（免费额度内）
若加做 speechocean762 引擎横评：5000 条 × ¥0.005 = **¥25**

## 四、要输出的表格

### 表 1：分数 × 星级（回答 P1）

| 竞技场 | 星级 | 朗读 A | 朗读 B | 朗读 C | 朗读 D | 均值 | 标准差 |
|---|---|---|---|---|---|---|---|
| ... | ⭐ | | | | | | |

**判定标准：**

| 结果 | 结论 |
|---|---|
| 分数随星级**明显递减** | ✅ 统一阈值成立，方案可行 |
| 分数各星级**差不多** | ❌ ⚠️ **统一 85 分阈值失效，征服体系需重新设计** |

> ⚠️ 这是唯一的**方案级风险**。若出现"分数不随难度下降"，整个「征服」机制要改。

### 表 2：分数分布（回答 P2）

- 全体样本的分数直方图
- 各星级的分数分位数（P10 / P25 / P50 / P75 / P90）

**判定标准：**

| 观察 | 阈值建议 |
|---|---|
| 多数样本 > 88 | ⚠️ 85 分门槛无意义，**需上调** |
| 多数样本 < 70 | ⚠️ 85 分太难，**需下调** |
| 目标：认真的学习者**够得着但需要努力** | 取**认真朗读样本的 P60–P75** 附近 |

### 表 3：ASR 识别率 × 口音水平（回答 P3）

| 朗读者 | 类型 | 参考词数 | ASR 识别词数 | 识别率 |
|---|---|---|---|---|
| ... | 好 / 中 / 重口音 | | | |

**判定标准：**

| 结果 | 结论 |
|---|---|
| 重口音样本识别率 > 60% | ✅ 预检第③层安全 |
| 重口音样本识别率 < 30% | ⚠️ **第③层会误伤，需放宽阈值或改用其他判据** |

### 表 4：重录意愿 × 竞技场长度（回答 P4）

| 竞技场 | 时长（秒） | 平均重录次数 | 放弃率 |
|---|---|---|---|
| ... | 8 / 12 / 20 / 30 | | |

**判定标准：**

| 观察 | 结论 |
|---|---|
| 某长度下重录次数骤降 / 放弃率骤升 | ⚠️ **该长度是上限**，竞技场应更短 |
| 各长度差异不大 | 10–20 秒可用，可选更长的以提高挑战性 |

### 表 5：真机技术验证（回答 T1/T2）

| 项 | iOS | Android | 结论 |
|---|---|---|---|
| onFrameRecorded 是否稳定回帧 | | | ⚠️ 任一平台失败 → 端侧架构需调整 |
| 帧间隔是否稳定 40ms | | | |
| Worker 中 FFT/自相关单帧耗时 | | | 目标 < 5ms |
| 录音格式是否严格 16k/16bit/单声道 | | | 否则 ISE 判"乱读" |

## 六、决策树

```
P1 分数随星级递减？
├─ 是 → 统一 85 分阈值成立
│         ↓
│      P2 分数分布 → 确定阈值（可能调整为 80 / 85 / 90）
│         ↓
│      P3 重口音识别率？
│      ├─ 高 → 预检第③层保留
│      └─ 低 → 放宽阈值或退回纯本地时长判断
│
└─ 否 → ⚠️ 方案级风险，征服体系需重新设计
         （改为按排名征服？按相对进步征服？需重新讨论）

T1 真机回帧稳定？
├─ 是 → 端侧架构成立，可以开工
└─ 否 → ⚠️ 端侧分析不可行，需改为「录音 → 上传 → 云端分析」
         （这会推翻「高频动作成本为 0」的前提，需重新设计）
```
