# 实验：端侧 DTW 对齐标准音 —— 能不能"标到你读到的那句词"

> **结论**：✅ **算法成立。** 用 macOS `say` 合成的两段朗读做了离线验证，
> 对齐路径能正确地在**长停顿处停住**，跟的是内容而不是时间。
>
> ⚠️ **但现有 MFCC 实现的性能不满足实时**：`dtw.ts` 里的
> `magnitudeSpectrum()` 是 **朴素 DFT，O(n²)**，实测 Node 下每帧 ~7.5ms，
> 按 iOS 慢 13 倍算 ≈ 100ms/帧，超过 64ms 的帧预算 —— **必须换成 FFT**。

---

## 为什么做这个实验

产品需求是「**我读到 girl，光标就标到 girl**」。
按时间估算做不到这件事（那是猜，不是识别）。
`spec.md:52` 原本定的方案就是：**逐词上色 = 端侧 DTW 对比标准音**。

但这条路有两个未知：
1. DTW 到底能不能对齐「不同人、不同语速、中间还卡壳」的朗读？
2. 端侧算得动吗？

这个实验回答的是第 1 个；第 2 个顺带量出来了。

---

## 实验方法

用 **macOS 自带 TTS** 合成两段朗读（无需联网、无需任何 API key）：

| | 声音 | 语速 | 文本 |
|---|---|---|---|
| **参考（标准音）** | Samantha | 175 wpm | The best way to predict the future is to invent it. |
| **输入（模拟用户）** | Alex | 130 wpm | 同上，但**句中插了 1.5 秒长停顿** `[[slnc 1500]]` |

处理链：`say` → `afconvert` 转 16kHz 单声道 16bit → `wavToPcm` → `frameAudio`(1024 采样/帧)
→ `mfccSequence` → 自写带 Sakoe-Chiba 窗的 DTW 累积矩阵 → 回溯路径。

**关键设计**：让「用户」在句中长停顿 —— 如果是按时间插值，比例会一直是常数；
**只有真正跟内容，才会在停顿处停住**。这是这个实验的判别点。

---

## 结果

```
标准音 2624ms ｜ 用户 5373ms（慢 25% + 中间 1.5s 停顿）
帧数：标准 41 ／ 用户 83

用户ms   标准ms   比例
   64       64   1.00
  704      512   0.73
 1344     1024   0.76
 1984     1152   0.58
 2624     1152   0.44   ← 停顿期间
 3264     1152   0.35   ← 标准时间卡住不动
 3904     1472   0.38   ← 停顿结束，恢复推进
 4544     2048   0.45
 5184     2496   0.48
```

**判别点通过**：用户从 1984ms 到 3264ms 这 1.28 秒里，标准时间一直停在 **1152ms** 不动 ——
对齐在停顿处**等待**了，而不是按比例往前走。恢复说话后又继续推进到句尾（2496ms ≈ 标准音全长 2624ms）。

---

## ⚠️ 顺带量出来的性能问题（必须先解决）

| 项 | 实测 |
|---|---|
| MFCC + DTW（Node，124 帧） | **936 ms** |
| 折合每帧 | **~7.5 ms** |
| 按 iOS 慢 13 倍（见 `AGENT.md` 的真机实测） | **~100 ms / 帧** |
| 实时预算（64ms 帧长） | **必须 < 64 ms/帧** ❌ |

**根因**：`dtw.ts` 的 `magnitudeSpectrum()` 是**朴素 DFT**，O(n²)。
1024 点 DFT ≈ 1M 次运算，而 1024 点 **FFT ≈ 1 万次** —— 差 **100 倍**。

> 注释里写着「小程序无 AnalyserNode，需自算」—— 自算没问题，但**必须用 FFT**。

### 解法（三步都很关键）

1. **实现 radix-2 FFT** 替掉朴素 DFT → 每帧降到 ~1ms（iOS），余量充足。
2. ⭐ **参考音的 MFCC 序列预计算**：标准音是固定的，它的 MFCC 完全可以在
   **内容流水线里算好**，直接写进 `ArticleContent`。
   于是设备端**只需要算用户自己那一帧的 MFCC**（1 次 FFT/帧），
   不用重复算标准音。
3. **在线 DTW**：每来一帧只更新累积代价矩阵的**一行**（对 M 个参考帧做距离，M ≈ 41~200），
   约几千次运算 —— 可忽略。

## 还没验证的（下一步）

| # | 问题 | 怎么验 |
|---|---|---|
| 1 | **FFT 版每帧耗时**在真机上到底多少 | 真机自检页加一项微基准 |
| 2 | **真实人声**（不是 TTS）对齐效果 | 需要真人朗读样本 |
| 3 | **读错/跳词**时对齐会不会乱 | 合成"跳读"样本 |
| 4 | 参考音里**没有的词**（用户自己加了词） | 同上 |
| 5 | **在线**（增量）版本与离线版的一致度 | 单测对比 |

> ⚠️ TTS 合成的"用户"是**过于理想**的：发音标准、没有口音、没有犹豫。
> 真人（尤其学习者）的对齐难度会更高。**结论 2 必须用真人样本复验。**

## 可复现

实验脚本用 `say` + `afconvert`，无外部依赖。核心链路：

```bash
say -v Samantha -r 175 -o std.aiff "The best way to predict the future is to invent it."
say -v Alex     -r 130 -o usr.aiff "The best way to predict [[slnc 1500]] the future is to invent it."
afconvert -f WAVE -d LEI16@16000 -c 1 std.aiff std.wav
# 再走 frameAudio → mfccSequence → DTW（见本次实验记录）
```
