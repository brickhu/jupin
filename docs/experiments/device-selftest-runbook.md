# 真机自检执行手册（T1–T6）

> 对应小程序里的「真机自检 T1–T6」页面。
> ⭐ **这是当前唯一的关键路径**——它验的是「端侧架构是否成立」这个方案级风险。

---

## 为什么先做这个

`docs/experiments/validation-experiment.md` 的决策树写得很直白：

```
T1 真机回帧稳定？
├─ 是 → 端侧架构成立，可以开工
└─ 否 → ⚠️ 端侧分析不可行，需改为「录音 → 上传 → 云端分析」
         （这会推翻「高频动作边际成本为 0」，需重新设计）
```

而它**不需要任何外部依赖**：

| 依赖 | T1–T6 需要吗 |
|---|---|
| 云托管 / 真机预览链路 | ❌ 不需要 |
| 讯飞 ISE 密钥 | ❌ 不需要 |
| 后端服务 | ❌ 不需要 |
| 局域网 / 同一个 Wi-Fi | ❌ 不需要 |
| **一部 iPhone + 一部 Android** | ✅ **只需要这个** |

所以它是整条链路上**成本最低、信息价值最高**的一步。云数据库那个阻塞不在关键路径上。

---

## 怎么跑

```bash
pnpm dev:mp          # 起构建监听（改代码自动重建）
```

然后：

1. 微信开发者工具打开 `apps/miniprogram`（`miniprogramRoot` 已指向 `dist/`）
2. 点工具栏 **预览** 或 **真机调试**，手机扫码
3. ⚠️ 首页会出现「登录失败」的日志——**这是预期的**，真机上连不到本机后端。
   `app.ts` 已刻意不弹 toast，避免误导。
4. 点首页底部的 **「真机自检 T1–T6 →」**
5. 点 **「开始自检（约 20 秒）」**，中间会提示你朗读一句话
6. 跑完点 **「复制报告」**，把文本贴回来

> ⚠️ **必须真机。** 开发者工具拿不到麦克风，且 `sampleRate` 参数在 PC 上无效。

## 测了什么

| 项 | 期望值 | 失败意味着 |
|---|---|---|
| **T1** | `onFrameRecorded` 有回调，5 秒约 78 帧 | ⚠️ **方案级风险**：端侧实时分析不可行 |
| **T2a** | 帧字节数 = 2048（`frameSize 2KB × 1024`） | 分帧假设不成立，缓冲逻辑要重写 |
| **T2b** | 帧间隔 ≈ 64ms | 同上；也可能是设备性能问题 |
| **T3+T4** | 反推值 = 16000 | 16000 → 16k 单声道 ✅<br>32000 → 双声道 ❌ 引擎判格式不符<br>8000 → 采样率没生效 ❌ 音频就是错的 |
| **T5** | 单帧 P95 < 5ms | 音高曲线不可行（但实测余量 300 倍以上，基本不会挂） |
| **T6** | 10/10 次 create→ping→terminate 成功 | Worker 泄漏，下次创建会失败 |
| **T6b** | 仅记录行为，不计通过/失败 | 探测性：只要 T6 稳定配对就不会走到这条路径 |

### T3/T4 的反推原理

录音 API 不直接告诉你采样率和声道数，但可以**反推乘积**：

```
每秒字节数 ÷ 2（16bit）= 采样率 × 声道数
```

| 实测值 | 解释 |
|---|---|
| 16000 | 16kHz 单声道 ✅ |
| 32000 | 16kHz **双声道** → `numberOfChannels: 1` 没生效 ❌ |
| 8000 | **采样率实际 8kHz** → `sampleRate: 16000` 没生效 ❌ |

⚠️ **只能测出乘积**，单靠这一项无法区分「16k 双声道」和「32k 单声道」。
所以页面还有一个 **「T3 精测」** 按钮：

它生成一段 **1kHz 标准音**（用 `pcmToWav` 编码后播放），同时录音，
再用 `detectPitch` 反推听到的频率：

- 检测到 **≈1000Hz** → 真实采样率确实是 16kHz ✅
- 检测到 **≈500Hz** → 真实采样率是 8kHz（1kHz 被折半）❌

