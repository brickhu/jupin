## 1. 通道选型

### 1.1 ⭐⭐ 先看这条：虚拟商品必须走「虚拟支付」

微信官方《虚拟支付：企业、个体户》产品介绍原文：

> 为保障用户权益，提高交易安全，开发者在小程序内提供的**虚拟商品**（包括**虚拟货币**、解锁功能、
> 订阅内容、付费功能、打赏、购买虚拟礼物等），购买和支付**均需接入小程序虚拟支付**。
> 适用于 **Android、iOS、鸿蒙、Windows 等所有终端**，iOS 端需使用微信客户端 8.0.68 及以上版本。

来源：https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html

**我们的能量 = 虚拟货币**（花点数换挑战次数），所以：

- ❌ 不能用普通微信支付（wx.requestPayment）卖能量 —— 包括**安卓端**
- ❌ 不能引导用户跳外部支付
- ✅ 只能用**虚拟支付**（wx.requestVirtualPayment），它会在安卓走微信支付、在 iOS 走 Apple 支付

### 1.2 那云托管封装的微信支付呢？

微信云托管确实封装了微信支付（POST http://api.weixin.qq.com/_/pay/unifiedOrder），免证书、免验签、
回调直接打到容器，看起来非常省事。但它**是普通微信支付**，只能卖给「实物 / 线下服务 / 物流类订单」。

| | 云托管封装的微信支付 | 小程序虚拟支付 ⭐ |
|---|---|---|
| 适用商品 | 实物、线下服务 | **虚拟货币 / 道具 / 会员 / 内容** |
| 商户号 | 我们已有的普通商户号 | **必须新开虚拟支付二级商户号** |
| 端侧接口 | wx.requestPayment | **wx.requestVirtualPayment** |
| iOS | ⛔ 不能用于虚拟商品 | ✅ 走 Apple 支付（Apple 佣金 12%） |
| 安卓费率 | 约 0.6% | 约 1%（腾讯技术服务费，2026 激励期） |
| 签名 | 云托管代签（免证书） | **自己签**：hmac_sha256(appKey, uri + '&' + signData) |
| 发货 | 自己处理回调 | 平台推送 + query_order 兜底 |
| 结算 | T+7 | **T+3**（iOS 由 Apple 结算，自然月后 45–60 天）|

⚠️ 云托管那条路的文档里也写明了它的定位：云托管在这里扮演的是「微信支付**服务商**」，
适合「支付收款、分账对账等基础能力」—— 它解决的是**怎么收钱**，不解决**能不能收这笔钱**。
合规边界是虚拟支付那条线划的，换通道不解决合规问题。

### 1.3 道具模式 vs 代币模式

虚拟支付给我们两种卖法，**选道具**：

| | 道具模式 ⭐ | 代币模式 |
|---|---|---|
| 商品在哪 | 微信侧「道具管理」里建道具（ID + 价格） | 微信侧「代币配置」里设代币名称 + 兑换比例 |
| 余额在哪 | **在我们自己库里**（users.energy） | **在微信侧**（query_user_balance / currency_pay） |
| 和现有能量模型 | 完全一致：买 → 加 energy + 写流水 | ⚠️ 会变成**第二份余额真相** |
| 改动 | 只加一个 xpay_product_id 映射 | 要重做「余额 / 扣减」两处，还要和 users.energy 对账 |
| 可改 | 道具可编辑后重新发布 | ⚠️ **代币兑换比例一旦发布不可修改** |

⭐ 决定性理由：**余额只能有一份真相**。代币模式会把余额搬到微信侧，
而我们的能量还有「每日补足 3 点」「奖励发点」「挑战扣 2 点」三种本地增减 ——
一旦有第二份余额，就必然出现「微信说 300、我们说 297」这种没法解释的差。

## 2. 商品与定价

### 2.1 三档（你给的售价）

| 商品 | 点数 | 售价 | 单价 | 每次挑战（2 点）| 相对首档 |
|---|---|---|---|---|---|
| energy_10 | 10 点 | ¥0.99 | ¥0.0990 / 点 | ¥0.198 | — |
| energy_300 | 300 点 | ¥19.90 | ¥0.0663 / 点 | ¥0.133 | 便宜 33% |
| energy_3000 | 3000 点 | ¥169.90 | ¥0.0566 / 点 | ¥0.113 | 便宜 43% |

梯度是合理的：三档之间是 10× / 10× 的量级跨度，单价单调下降，最大档比首档便宜 43%。

### 2.2 ⚠️ 但 ¥0.99 这一档在 iOS 上卖不了

官方 iOS 下单条件里有一条硬约束：**最低支付金额为 1 元**。

¥0.99 < ¥1 ⇒ **iOS 用户买这一档会直接失败**（而且是在拉起 Apple 支付那一刻才失败，
用户看到的是「支付失败」，我们会收到一堆不知道为什么失败的工单）。

道具的价格是**跨端通用**的（官方：「开发者配置的道具、代币均为 Android、iOS 双端互通」），
所以不能「安卓 ¥0.99、iOS ¥1.00」两套价。

**建议：首档改成 ¥1.00 / 10 点。** 理由：

- ¥0.99 的心理价位靠的是「不到一块钱」，而 ¥1.00 和它的差距只有 1 分钱，认知上仍属同一档
- 反过来（iOS 隐藏首档）会让 iOS 用户**买不到最便宜的档**，是最差的选择
- 若以后一定要保留 ¥0.99，只能让它变成「安卓专享」，那就要在端侧分叉 UI —— 不值得

⚠️ 这条请你拍板（见 §10 待定 1）。

### 2.3 单位经济（成本对照）

| 项 | 单次挑战 |
|---|---|
| 收入（按最贵档 ¥0.198 / 次，最便宜档 ¥0.113 / 次）| ¥0.113 – 0.198 |
| 讯飞 ISE 评测成本（30 秒音频一次，项目内调研结论）| ≈ ¥0.0015 – 0.006 |
| 渠道费 · 安卓（约 1%）| ¥0.001 – 0.002 |
| 渠道费 · iOS（Apple 12%）| ¥0.014 – 0.024 |

⇒ 即使按最贵的评测 + iOS 佣金算，毛利仍在 80% 以上。**打分成本不构成定价约束**，
真正的约束是「免费用户每天补 3 点」这个获客成本（一个人每天送 1–2 次评测）。

（讯飞单价来自 docs/research/speech-eval-vendor-comparison.md；渠道费率来自官方虚拟支付文档与公开解读，
标注为**参考值**，签约时以合同为准。）

### 2.4 商品目录放哪：落库，不是常量

⭐ 结论：**落库（goods 表）+ 种子**，与 reward_rules 同一套模式。理由：

1. **改价不该发版**。小程序审核 1–3 天，促销/调价绑在发版上就废了
2. **价格有两个源头**（我们的展示 + 微信侧道具），落库才能集中对账
3. 与本项目已有的「奖励规则落库」是同一个判断：**能被运营改的东西不要写死在代码里**

⚠️ 但**下单时必须快照**（payments 里存 goods_code / 点数 / 金额）：
商品表以后改了，历史订单必须还是当时那个商品 —— 这就是「改配置不追溯」。

## 3. 数据模型

### 3.1 goods（新表）

| 列 | 说明 |
|---|---|
| code | 商品码，主键式唯一：energy_10 / energy_300 / energy_3000 |
| kind | **energy / unfreeze** —— 解冻卡以后不改接口，只加一行商品 |
| amount | 发多少（点 / 张）|
| price_fen | 售价，**单位分**（1990）。⚠️ 必须与微信侧道具价格一致 |
| xpay_product_id | 微信侧道具 ID（道具管理里创建时拿到的）|
| title / subtitle | 展示文案（端侧只渲染，不判断）|
| badge | 角标文案，可空（如「最划算」）|
| sort / enabled | 排序与上下架 |

⭐ 端侧价格也从这里来（GET /api/shop/goods），不在小程序里写死 —— 否则改价要发版。

### 3.2 payments（已有表，要改）

现有列大多能用（out_trade_no / amount / status / transaction_id / raw_notify / refund 三兄弟），要改的是：

| 改动 | 说明 |
|---|---|
| plan → **goods_code** | plan 的语义是 monthly/yearly（旧包月模型），现在卖的是商品码。⚠️ 改名 + 迁移要拆两次 generate（drizzle-kit 会弹交互式 rename 提问）|
| 新增 **goods_kind / goods_amount** | 点数快照。以后商品改了，订单还是当时那个 |
| 新增 **xpay_order_id** | 微信侧单号（虚拟支付的 wx_order_id），对账/查单用 |
| 新增 **env** | 0 = 现网 / 1 = 沙箱。⚠️ 同一个 out_trade_no 在沙箱和现网是两个世界 |
| 新增 **delivered_at** | 货什么时候发的。paid 是「钱到了」，delivered 是「货发了」，两件事 |
| status 取值 | pending / paid / refunded / failed / closed |

### 3.3 energy_ledger（不用改，直接用）

⭐ 买能量就写一行：reason='purchase'、ref_type='purchase'、**ref_id=out_trade_no**、delta=+N。

它的唯一键 (reason, ref_type, ref_id, user_id) **天然就是发货的幂等键** ——
发货推送重推 15 次、我们并发处理，都只会加一次能量。这一点不需要新机制。

### 3.4 users（加一列）

| 列 | 说明 |
|---|---|
| **session_key** | 虚拟支付的**服务器 API 要用户态签名**（hmac_sha256(session_key, signData)）。现在服务端**完全没有处理过 session_key**（只用了 openid）|

⚠️ session_key 是敏感凭证（等同于登录态），且会过期；它只能从 auth.code2Session 拿。
⚠️ 我们的线上主通道是 callContainer（openid 由网关注入），**这条路上拿不到 session_key**。
⇒ 方案见 §5.2：需要时由端侧补一次 wx.login。

## 4. 完整链路

### 4.1 买一次能量要经过什么

~~~
① 端侧：用户在 me/energy 点「¥19.9 买 300 点」
② 端侧 → 服务端：POST /api/shop/order { goodsCode: 'energy_300' }
     服务端：查商品（必须在售）→ 生成 outTradeNo（= 幂等键）
             → 落一行 payments(status=pending, 快照点数/金额)
             → 调虚拟支付服务器 API 下单 → 拿 wx_order_id
             → 算 paySig / signData → 返回 payData
③ 端侧：wx.requestVirtualPayment(payData)
     · 安卓/鸿蒙/Windows → 微信支付拉起
     · iOS → Apple 支付拉起（用户需 iOS 15+ / 微信 8.0.68+ / 金额 ≥ 1 元）
④ 支付成功 → 平台向我们推送 xpay_goods_deliver_notify
     服务端：校验 → 幂等 → 一个事务里：
              payments.status = paid + xpay_order_id + paid_at + delivered_at
              users.energy += N
              energy_ledger 写一行（幂等键 = out_trade_no）
     返回 {"ErrCode": 0}
⑤ 端侧：支付 success 回调 → 只做「提示 + 刷新余额」，**不作为发货依据**
~~~

⚠️⚠️ 端侧的 success 回调**可能丢失**（微信异常退出），官方原文要求
「发货以发货推送为主，推送丢失时用 query_order 查单兜底」，
并且明确「**前端支付回调不作为发货依据**」—— 绝不能靠它发货。

### 4.2 服务端接口（我们的）

| 接口 | 作用 |
|---|---|
| GET /api/shop/goods | 商品列表（含价格、点数、角标）。端侧渲染充值卡片 |
| POST /api/shop/order | 下单，返回 payData |
| POST /api/shop/order/:outTradeNo/check | 「我付了但没到账」→ 主动查单补发 |
| GET /api/user/energy | 余额 + 流水（分页）—— me/energy 页用 |
| POST **/api/pay/notify** | ⭐ 平台发货推送的落点。**必须在鉴权中间件之外**（平台不带我们的 token）|

⚠️ /api/pay/notify 是本项目**第一个不在 authMiddleware 后面的写接口**。
它必须自己解决「这条推送是真的吗」——见 §5.3。

## 5. 签名与安全

### 5.1 支付签名（我们 → 微信）

~~~
paySig = hex( hmac_sha256( appKey, uri + '&' + signData ) )
~~~

- wx.requestVirtualPayment 的 uri 固定填 requestVirtualPayment
- 调服务器 API 时 uri = 接口路径（如 /xpay/query_order），**不带 query string**
- appKey 分**沙箱**与**现网**两把，由 env 决定（env=1 → 沙箱，env=0 → 现网）
- ⚠️ 参与签名的 signData 必须**与实际发出的 body 逐字节一致**（序列化差异会直接导致签名错）

### 5.2 用户态签名（我们 → 微信，代表某个用户）

~~~
signature = hex( hmac_sha256( sessionKey, signData ) )
~~~

⚠️ sessionKey 只能从 auth.code2Session 拿，而我们的 callContainer 通道**没有它**。
⇒ 设计：下单接口接受一个可选的 loginCode；没有有效 session_key 时，
   端侧先 wx.login 拿 code 一起传上来，服务端换一次 session_key 并落库。
   （这也是「用户态签名」这个名字的意思：它代表的是**这个用户**同意这笔操作。）

⚠️ 待核实：**是否每个服务器接口都需要用户态签名**。官方示例只对 query_user_balance 演示了两种签名。
实现第一步就是拿沙箱环境把 query_order 单独打一遍，确认要哪几个签名 ——
**先证明链路通，再写业务**（同「先探针后实现」的既有做法）。

### 5.3 发货推送怎么验真

推送会打到我们的公网 URL，所以**任何人都能往这个地址 POST**。三层防线：

1. **查单为准**：收到推送后，用 out_trade_no 调 query_order 反查一次，以微信的答复为准发货。
   （最贵但最稳；对付伪造推送一步到位）
2. **金额对账**：推送里的 ActualPrice 必须 == 订单快照的 price_fen，不一致就**不发货**并告警
3. **状态机**：只有 pending 的订单能变 paid；已 paid 的直接返回成功（幂等）

⚠️ 恒等式的另一半：推送里的 OutTradeNo 必须**在我们库里存在**且属于这个 OpenId ——
   不存在就丢弃 + 告警（伪造或串环境的典型特征）。

### 5.4 响应格式（这个错了会被重推 15 次）

~~~
JSON：{"ErrCode": 0, "ErrMsg": "success"}
XML ：<xml><ErrCode>0</ErrCode><ErrMsg><![CDATA[success]]></ErrMsg></xml>
~~~

⚠️ 格式不对（或返回空但平台不认）→ 按 2/4/8/16… 的间隔**最多重推 15 次**。
所以「重推」是常态而不是异常：处理逻辑必须**天然幂等**，且**永远返回成功**，
除非我们真的希望它再推一次（比如自己数据库挂了）。

## 6. 对账、退款、边界

### 6.1 三种「没到账」

| 现象 | 处理 |
|---|---|
| 用户付了、推送没到 | 用户在 me/energy 点「我付了但没到账」→ 我们 query_order → 补发 |
| 用户下单了、一直没付 | 订单停在 pending。⚠️ 用户下次下单会生成**新单号**，旧单自然烂掉（不影响余额）|
| 推送到了、我们写库失败 | 返回**非 0**（让平台重推）—— 这是唯一该返回失败的情况 |

⭐ 还可以加一条**惰性兜底**：进 me/energy 页时，把 5 分钟前仍 pending 的订单各查一次单。
不做定时任务（本项目没有定时器基建），复用用户自己的访问频率。

### 6.2 退款

| 端 | 规则 |
|---|---|
| 安卓等 | 我们可调 /xpay/refund_order 主动退；180 天内的退款平台退还手续费 |
| **iOS** | ⚠️ **Apple 支付不允许开发者主动退款**。用户只能去 App Store 申请，Apple 会向我们发起**最多 3 次退款问询**（xpay_subscribe_ios_refund_query_notify），我们要在 **3 秒内**应答，否则平台替我们回「不确定」|

⇒ 必做：实现退款问询的应答接口（可返回「已发货、拒绝退款」或「放过」）。
⚠️ **3 秒**是很紧的：接口里不能做任何慢查询。默认策略建议：**已发货就拒绝**（附凭据 = 该订单的评测已消耗），
因为我们的商品是**即时消耗型**的（买了就用来打分）。

### 6.3 能量被消耗后退款怎么办

建议（MVP）：**钱退、能量扣回；余额不够就扣成负数**（负数余额 = 欠账，下次充能先补上）。
理由：拒绝退款的体验更差，而扣成负数在系统里是自洽的（余额本来就是整数，允许负）。
⚠️ 这条要你拍板（见 §10 待定 3）。

## 7. 客户端：pages/me/energy

放在 me/ 下（**只给自己看**，与对外展示的 pages/profile 相反）。

| 区块 | 内容 |
|---|---|
| ① 余额 | 大字 ⚡ N 点 + 一句「每次挑战消耗 2 点」+ 「每天补到 3 点」 |
| ② 充值 | 三张卡片（点数 / 价格 / 单价 / 角标「最划算」）；点了就走 §4.1 的链路 |
| ③ 流水 | 时间 + 变动（+300 / −2）+ 原因文案 + 余额（可选）|
| ④ 兜底 | 「付了没到账？」→ 查单补发 |

⚠️ 定价卡片的价格**从接口来**，不写死在小程序里（理由见 §2.4）。

流水的原因文案（reason → 中文）全部由端侧映射，**服务端返回 reason 原文**：

| reason | 文案 |
|---|---|
| purchase | 充值 |
| daily_topup | 每日补足 |
| challenge_hold | 挑战（冻结）|
| challenge_release | 挑战失败退回 |
| streak_unfreeze_7 等奖励码 | 连战奖励 等（规则表里配置的名字）|

⚠️ hold / release 是**成对**的：挑战成功时 hold 之后会被结算成实扣，失败时 release 退回。
流水页要不要把这一对折叠起来显示，是一个展示问题 → §10 待定 4。

## 8. 本地开发怎么办

## 9. ⭐ 你要去配置的通道（清单）

### 9.1 微信支付侧（新开虚拟支付商户号）

1. **确认小程序主体**：企业 / 事业单位 / 个体工商户（个人主体另有一条路，但要求服务类目含「工具」，且月限额 10 万）
2. **MP 后台 → 左边栏【虚拟支付】→ 开通**：签协议 → 提交营业执照 / 对公提现账户 / 支付管理员 → 审核 1–7 个工作日
3. **账户验证 + 扫码签约**（管理员微信扫码）→ 约 1–2 个工作日后状态变「已签约」
4. ⚠️ **这一步会新开一个二级商户号** —— 你说的「现成的商户号」用不上（官方文档原文：
   「可通过小程序管理后台 - 虚拟支付模块，**开通一个新的微信支付商户号**」）
5. **道具管理**：建三个道具（10 / 300 / 3000 点）并**发布到现网版本**，记下三个**道具 ID**
6. **基础配置**里拿三样东西：**AppID / OfferID / 现网 AppKey**（另有沙箱 AppKey）
7. ⚠️ **iOS 额外条件**：配置**小程序简称**（Apple 要展示 display name），然后在虚拟支付-基础配置里开通 iOS 支付
8. **发货推送（消息推送）URL**：填我们的 https 回调地址（云托管域名 + /api/pay/notify）

### 9.2 我们这边

| 要配的东西 | 值 / 来源 |
|---|---|
| XPAY_OFFER_ID | 虚拟支付-基础配置 |
| XPAY_APP_KEY / XPAY_SANDBOX_APP_KEY | 同上（两把，按 env 选）|
| XPAY_ENV | 0 现网 / 1 沙箱 |
| 三个道具 ID | 道具管理（写进 goods.xpay_product_id）|
| 回调 URL | https://<云托管域名>/api/pay/notify |

⚠️ 上面四项都是**密钥级**，走既有的 tools/gh-secrets.mjs 一起进 GitHub Secrets + 服务环境变量。

### 9.3 ❌ 不需要配的（省得你去折腾）

- ❌ 不需要 APIv3 密钥、apiclient 证书（虚拟支付用 appKey 签名，不走证书）
- ❌ 不需要在云托管控制台配「微信支付配置」（那是**普通**微信支付那条路）
- ❌ 不需要开「开放接口服务」（虚拟支付不走 api.weixin.qq.com 的云调用封装）
- ❌ 不需要实物电商那套发货信息管理 / 确认收货组件

⚠️ 最后一条要**核实一次**：我们原以为要走云托管封装（那才需要开放接口服务）。
虚拟支付是独立的一套 HTTP API（/xpay/*），按文档不需要开放接口服务。会上线前用沙箱验一次。
