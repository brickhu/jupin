### 1.1 f —— 三个指标共用的换算函数

~~~
f(x) = clamp(Math.round(x), 0, 10)
~~~

- step = 1，四舍五入
- 值域 [0, 10]
- ⚠️ 两个例外：鹤立鸡群**和**自我超越的 n1 都在 f 之后再乘样本量权重 w（见 1.4），
  所以它们的值域不受 10 约束

### 1.2 自我超越（selfSurpass）

**两个维度各算一个分，最后取平均：**

~~~
// ① 场内：跟「我在这句上的历史最高分」比
n1 = highestInSentence > 0 ? f(score − highestInSentence) : 0

// ② 全局：跟「我的个人历史最高分」比
n2 = highestInUser > 0 ? f(score − highestInUser) : 0

// ③ 合成
selfSurpass = round((n1 + n2) / 2)
~~~

- 「f(x) = clamp(round(x), 0, 10)」（见 1.1）
- ⚠️ 自我超越**不乘 w** —— w 只属于鹤立鸡群
- 值域 [0, 10]

⭐⭐ **没有 75 下限**（这条改过两次，最终定为「没有」）：基准就是历史最高分本身。
**没有历史（= 0）时这一维直接不成立、给 0** —— 不是「以 75 为参考坐标」。

两个直接后果：

| 场景 | 结果 |
|---|---|
| 新人第一次读任何句子 | 两个维度都没有历史 ⇒ **自我超越 = 0** |
| 我在这句最高 56、这次 60 | n1 = f(4) = 4 —— **60 分不到 75 也算超越** |

⭐ **为什么取平均而不是 max**：因为「我在这句的最高分」永远 ≤「我的全局最高分」
⇒ **n1 ≥ n2 恒成立**。取 max 的话 n2 永远取不到（那一维是空的）；
取平均之后 n2 虽然也永远不会超过 n1，但它会**把分数往下拉** ——
**两边都破纪录才拿得满**，这一维因此不是摆设。

**例子 1**：我在这句历史 56 / 73 / 45（最高 73）；个人全局最高 95；这次 82
- n1 = f(82 − 73) = **9**
- n2 = 82 − 95 < 0 → **0**
- **selfSurpass = round((9 + 0) / 2) = round(4.5) = 5**

**例子 2**：全新用户，第一次读任何句子，得 80
- n1 = 0（这句没有历史），n2 = 0（个人也没有历史）
- **selfSurpass = 0** ← 新人第一次读拿不到自我超越，符合「新用户成长值都是 0」

**例子 3**：我在这句最高 80；个人全局最高 85；这次 92（**两边都破**）
- n1 = f(12) = **10**，n2 = f(7) = **7**
- **selfSurpass = round(8.5) = 9** ← 两边都破才拿得高，这正是取平均的意义

**例子 4**：我在这句最高 80；个人全局最高 95；这次 90（**只破句内**）
- n1 = f(10) = **10**，n2 = 0
- **selfSurpass = round(5) = 5** ← ⚠️ 只破一边，最高也只能拿到一半

**边界**：
- 没有历史 ⇒ 该维度 0；两个维度都没有历史 ⇒ 自我超越 0
- baseB 包含当前句的历史（它就是「个人最好成绩」，不排除任何句子）
- ⚠️ 需要四舍五入 —— 平均必然产生 .5（Math.round(4.5) = 5，向上）

### 1.3 孜孜不倦（diligence）

**里程碑式，跨过即给一次；中断后重新攒，档位从头开始。**

| 跨过 | 奖励 | 连续不断的累计 |
|---|---|---|
| 7 天 | +1 | 1 |
| 30 天 | +5 | 6 |
| **180 天** | **+40** | **46** |
| 360 天 | +100 | 146 |
| 720 天 | +200 | 346 |
| 1080 天 | +400 | 746 |
| 1440 天 | +800 | 1546 |

**公式**：第 k 个 360 天里程碑 → +100 × 2^(k−1)

**判定方式**（在 recordRead 里，用 before / after 两个 streakDays 判跨档）：

~~~
if (before <= 7   && after > 7)    +1
if (before <= 30  && after > 30)   +5
if (before <= 180 && after > 180)  +40
k = 1,2,3...
if (before <= 360*k && after > 360*k)  +100 * 2^(k-1)
~~~

⚠️ 必须用 before/after 判定，**不能**写成「现在 streakDays > 7 就给」——
那样每次读都会给一次。这样写才能做到「每个连续周期只触发一次」。

⚠️ **「跨过」= after > 阈值，所以档位落在"阈值 + 1"那一天**：
7 档在第 **8** 天、30 档在第 31 天、180 档在第 181 天、360 档在第 **361** 天。
表格表头写「7 天」是「跨过 7 天」的意思 —— 与「streak > 7」这句原话一致。
（⚠️ 别和奖励规则 A 搞混：那条判据是 **>= 7**，第 7 天就发卡。两条规则口径本来就不同。）

**为什么 k 随中断重置**：与 7/30 档保持同一条规则 ——
「中断了但有 3 次 streak>7 → 1+1+1」正是这条规则。推论：
一个连续周期到 800 天 = 1+5+40+100+200 = 346；
**断了再来一次 800 天 = 346 × 2 = 692**，
仍低于一口气 1500 天的 **746**。中断有代价，但不会一笔抹掉。

**长期坚持是指数级上升的**（这是刻意的）：折算下来，
孜孜不倦一年 = 146，两年 = 346，三年 = 746。它会是成长值里最大的一块 ——
而鹤立鸡群单次最多 12（见 1.4），自我超越单次最多 12。**量级是设计出来的，不是碰巧。**

### 1.4 鹤立鸡群（standout）

**基准 = 提交那一刻的榜单中位数，按样本量加权。**

~~~
snapshot = 该场**榜单上的分数**（每个参与者取历史最高分，一人一条）
m        = median(snapshot) || 75        // 空 → 75（⭐ 这条兜底是真在用的，见下）
w        = 由 snapshot.length 决定

standout = round(f(score − m) * w)
~~~

| snapshot.length | w |
|---|---|
| **0 – 9** | **0.5** |
| 10 – 99 | 0.8 |
| 100 – 999 | 1.0 |
| ≥ 1000 | 1.2 |

（左闭右开区间：[0,10) [10,100) [100,1000) [1000,∞)）

⭐ **snapshot 取「榜单分数」**：用户可能在同一句挑战 100 轮，
但**只有最高分那一次上榜** —— 所以是**一人一条**，不按提交次数算。
两个好处：与榜单同口径（用户能自己核对自己的位置）；
也不会被一个人反复读把 w 顶到 1.2、把中位数拉低（那等于替别人刷分）。

⭐⭐ **空样本（n = 0）给 w = 0.5，不给 0** —— 这是刻意的：
**鼓励用户成为新竞技场里的第一个人。**
正因如此，那个「|| 75」的兜底是**真的在用的**：新场子的第一个参与者，
基准就是 **75** 这条线，而不是"没有基准所以 0 分"。

⚠️ **0 和 1–9 是同一档（都是 0.5）**，所以「做第一个」的好处**只体现在基准上**：
第一个人的基准是固定的 **75**，从第二个人起基准就被前面的人抬着走了。
这是"软鼓励"，不是"重奖第一"。



| 场景 | snapshot.length | m | 你得 | f(d) | w | standout |
|---|---|---|---|---|---|---|
| **你是第 1 个** | **0** | **75**（兜底） | 80 | 5 | **0.5** | **3** |
| 小场 | 10 | 70 | 80 | 10 | 0.8 | **8** |
| 中等场 | 100 | 78 | 85 | 7 | 1.0 | **7** |
| 大场 | 1000 | 82 | 90 | 8 | 1.2 | **10** |

**为什么要有 w**：同样是「比中位数高 5 分」，在 10 个人里和在 1000 个人里含金量不同；
而且人少时中位数本身极不稳定（3 个人的中位数就是中间那一个人的分）。

**口径细节**：
- 快照**包含本人**的历史 —— 它就是「场上的中位数」，你本来就是场上的一员。
  ⭐ 附带好处：重复挑战时你自己的高分会把中位数抬上去，**这条指标自我限制**
- 边界用**左闭右开**（见上面的档位表）
- ⚠️ 四舍五入的边界：w=0.5、f=1 时 Math.round(0.5) = 1，小场的最低奖励仍是 1 分。
  可接受（不是 0），记在这里备查

### 1.5 三指标的共同规则

1. **只统计 status='scored' 的提交**（与榜单、额度同一口径）。
2. **必须落快照**。这三个数依赖「当时的历史」，而历史会变 ——
   不落库的话，同一个成绩今天显示 +5、明天显示 +3，用户会认为是 bug。
   每次提交把这些一起写进 submissions 并**永久冻结**：
   prevA / prevB / A / B / n / m / w / standout / diligence 增量。
3. **分开展示，不合成总分**。三个数各自回答一个问题，相加之后没人解释得清那个数怎么来的。
4. **累加值落 users**（热读），每次提交的明细落 submissions 快照（可复现）。

## 2. 能量值

### 2.1 为什么不能沿用现在的实现

现在（services/quota.ts）：免费 1 次 / 付费 50 次，**每天重置**，
usedToday 是在 dailyChallengeUsage() 里**从 submissions 现算**的。

改成能量之后，**余额要跨天留存** —— 昨天剩下的点数今天还在（这是那个钩子的全部意义）。
现算的路走不通了，**必须落库**：余额 + 流水。

### 2.2 账户模型

**只有一个整数口径，不引入任何小数**。理由不只是「浮点迟早出现 0.9999999」，
更是「能量」和「单位」两层口径会让每一处都要多问一句「这是哪一个」：

~~~
每日补足下限 = 3 点
每次挑战消耗 = 2 点
购买起步单位 = 10 点     // 充值的最小单位；档位（10 / 30 / 100…）后定
~~~

⭐ 3 和 2 不是随手取的：**免费用户每天挑战一次之后正好剩 1 点**，
那个 1 点就是钩子本身 —— 而一次行为奖励正好是 **+1 点**：
**「剩 1 + 奖励 1 = 再来一句」**（见 2.3）。

⚠️ **发放没有最小刻度**：1 点就是有意义的。只有**购买**才有起步单位（10 点）。

| 位置 | 内容 |
|---|---|
| users.energy | 余额（整数，热判断用） |
| users.energyDate | 最后一次补足的日期 YYYY-MM-DD（惰性补足用） |
| energy_ledger 表 | 流水：userId / delta / reason / refType / refId / createdAt |

⚠️⚠️ **流水是真相，余额是缓存**。两者必须**在同一个事务里**写。
分开写就一定会漂移 —— 而「余额和流水对不上」是最难查的一类问题。

**没有上限**：充值来的能量不过期、不清零。免费用户不充值的话天然封顶在 3 点
（因为补足是 max，不会累积）。

### 2.3 每日补足（惰性 + 幂等）

不引入定时任务。在**读余额和提交**这两条路径上顺手结算：

~~~
if (users.energyDate != today) {
  energy = max(energy, 3)      // 补到 3 点，但不抹掉充值/奖励来的余额
  energyDate = today
}
~~~

⭐ **剩的那 1 点是钩子**：免费用户每天补到 3 点，挑战一次扣 2 ⇒ 手里永远剩 1 点，
永远差 1 点才能读第二次。而一次行为奖励正好是 **+1 点**：
**剩 1 + 奖励 1 = 2 = 再来一句** —— 钩子的刻度和奖励的刻度是对齐的。

⚠️ UI 不要只显示一个余额数字，要说清「还差多少」：
「⚡ 1 点 · 再攒 1 点就能再读一句」比「⚡ 1」有用得多。
一个永远花不掉的 1 点，如果不说清它的用途，会被理解成「这 1 点是假的」。

### 2.4 消耗：锁 → 结算（两阶段）

这是两个问题，不要混：

| | 问题 | 结论 |
|---|---|---|
| **A 锁** | 提交时要不要先占住这 2 点能量 | **要**。防并发提交把同一份能量用两遍 |
| **B 结算** | 什么时候真的扣掉 | **接口返回结果决定**：成功实扣，失败解锁退回 |

~~~
① 提交受理
   原子锁：UPDATE users SET energy = energy - 2 WHERE id = ? AND energy >= 2
   affected = 0 → 429 ENERGY_EXHAUSTED（不进队列、不调用引擎）
   写流水：-2, reason='challenge_hold', ref=submissionId
   submission.energy_state = 'held'

② 引擎返回
   成功（status='scored'）  → energy_state = 'charged'（流水不动，hold 就是最终状态）
   失败（status='failed'）  → 余额 +2；流水 +2, reason='challenge_release'
                              energy_state = 'released'

③ 幂等重放（同一段音频重试，走 replay 分支）
   → 不锁、不结算（引擎根本没被再调用）

④ 轮询取结果 → 不涉及
~~~

⚠️ 锁必须**绑定到那条 submission**（held / charged / released 三态），
否则打分任务崩了、进程重启了，那 2 点能量会永久卡在「锁住」状态 ——
用户看到余额少了，却没有任何东西能解释它去哪了。

⚠️ 必须有**兜底回收**：任务超时 / 进程重启后，扫描停在 held、
而 submission 已经 failed 或心跳超时的行，释放它们。

⚠️ 用户可见的说法：「这次检测没通过，**能量已退回**」。
（讯飞那边失败也可能计费 —— 那是我们承担的成本，不转嫁给用户。读不出来还扣钱，解释不通。）

### 2.5 收入

**充值**（包月暂时不做）：**起步单位 10 点**（= 5 次挑战），reason='purchase'，ref=**out_trade_no**（比自增 paymentId 更适合做对账键 —— 见 docs/design/payment-and-purchase.md）。
⚠️ 单价与档位（10 / 30 / 100 …）属于销售策略，**先留架构、后定价**，但**最小单位写死 10**。

**行为奖励**：例如「新竞技场前 3 个参与者 **+1 点**能量」——
正好补齐免费用户手里那 1 点（见 2.3）。

⚠️ 奖励**没有最小刻度**，1 点就是有意义的（它是"还差一点"的那一点）。

⚠️ 必须幂等：唯一键 unique(reason, ref_type, ref_id, user_id)，或等价的一次性发放标记。
否则重放、补跑、并发都会多发。

## 6. 存量数据

### 6.1 结论：不回溯，并且把历史数据清掉

**产品还没上线** —— 现有的 submissions、战绩、streak 全部是测试数据，
没有任何一条值得保留。所以不做回溯，直接清空。

（「回溯」= 拿历史提交按新公式重算、把成长值补上。不做的理由：
鹤立鸡群的基准是「提交那一刻的场上中位数快照」，那个快照**当时没有存**，
现在只能用今天的数据去回算当时 —— 算出来的数与真实口径不同，
**因此不可解释**：用户问「我这里为什么是 +8」，我们答不上来。）

### 6.2 清哪些（⚠️ 最后一条最容易漏）

| 清什么 | 为什么 |
|---|---|
| submissions 全表 | 成绩历史，全部是测试数据 |
| users 的 streak_days / streak_best / last_read_date、以及解冻卡表 | 它们是从 submissions 推出来的。清了成绩再留着这些数就是孤儿 —— 「连战 12 天」而一条提交都查不到 |
| users 的 invalid_count / invalid_date / growth_* / energy / energy_date | 同上（新列本来也是 0，这里是显式兜底） |
| **articles 的 participant_count / conquered_count** | ⚠️⚠️ **最容易漏的一条**：它们是 submissions 的**冗余计数**。不清的话竞技场会显示「19 人参与」而底下一条成绩都没有 —— 正是「两个数对不上」的那类 bug |
| 探针 / 测试账号（dev 的 probe_login_e2e 之类） | 手工造的账号 |
| energy_ledger | 新表，本来就是空的 |

**保留不动**：articles 的正文 / 音频 / 发布状态、schedules 排期、用户本人的昵称头像。

**能量不用回填**：列默认 0，第一次访问时惰性补足会自动给到 3 点。
本地 dev 环境另发一大笔（否则只有 3 点，什么都测不了）。

### 6.3 怎么做

⭐ **一次性脚本，不进 migrations**（tools/wipe-history.mjs）。
理由：migration 会在每次 AUTO_MIGRATE 时被检查执行，也会在别人重建库时被重放 ——
一条 DELETE 留在迁移历史里，迟早会清掉不该清的东西。一次性脚本跑完即作废。

⚠️ **脚本必须先 SELECT COUNT 打印、再要求显式传 --yes 才真的删。**
「跑一个脚本把线上数据清了」这件事不该能误触。

⚠️ dev 和 prod 都要跑一遍（prod 库里也有测试提交）。

### 6.4 时机

放在**迁移之后、客户端改动之前** —— 这样后面每一次验证都跑在干净数据上，
不会出现「这个 0 是 bug 还是旧数据」的犹豫。

⚠️⚠️ **但云上（dev / prod）的「迁移 + 清理」必须跟新服务端代码一起上，不能提前。**

原因：迁移 0017 会 **DROP users.freeze_count**，而线上跑着的**旧代码还在 SELECT 它** ——
先迁库就是当场把 dev/prod 打挂（每次取用户都炸）。所以云上的顺序是：

    deploy（新代码 + AUTO_MIGRATE 自动跑迁移）  →  立刻跑 wipe-history

本地没这个问题（本地服务是自己随手起的，代码和库一起改），所以本地随时可以迁。

实操记录：
- 本地：已迁（0016 / 0017）+ 已清（302 条成绩、5 张被污染的竞技场计数归零）
- dev / prod：**待部署时一起做**

⭐ 这条与「新用户成长值都是 0」是同一条规则：**成长值从上线那一刻开始记。**

## 7. 测试清单

**shared 纯函数**（这次的核心可测面）
- f：0.4 / 0.5 / 9.6 / −3 / 99 的取值
- 自我超越·句子级：无历史 → 基准 75；有历史 → 基准是**中位数**不是最高分（88/92/75 → 88）
- 自我超越·用户级：无历史 → 基准 75（不是 0）；基准是**个人全站最高分**
- 自我超越·合成：取 max 不是相加（两个维度都破纪录时只算一次）；**只在最后四舍五入一次**
- 自我超越值域：[0, 12]（n1 上限 12、n2 上限 10）
- ⚠️ 刷分路径的回归测试：90/60 交替 → 每两次拿一次满额 n1（记录现状，防的是"以为不可刷"）
- 孜孜不倦：跨 7 / 30 / 180 / 360 / 720 各触发一次；同一档不重复触发；中断后重新触发（1+1+1）
- 孜孜不倦的**档位顺序**：180 的 +40 在 360 的 +100 之前，别按数值大小排错（阈值升序、奖励跳变）
- 鹤立鸡群：n=0 → 基准 75、w=0.5（**不是 0 分**）；w 的档位边界（9 / 10 / 99 / 100 / 999 / 1000）；Math.round 边界
- 能量：每日补足幂等、max(energy, 3) 语义（充值余额不被抹掉）、扣 2 之后余额正确
- 购买刻度：任何充值档位都是 ENERGY_PURCHASE_MIN = 10 的整数倍
- 自我超越的 75 硬指标：无历史时基准是 75（得 80 → A = 5；得 70 → A = 0）

**服务端**
- 原子锁：余额 3 时并发两次提交，只有一次能锁到（第二次只剩 1 点，锁不动）
- 失败释放：failed 之后余额恢复、流水成对（hold + release）
- 幂等重放：同一段音频重试**不重复扣**
- 兜底回收：held 且心跳超时的 submission 被释放
- 奖励幂等：并发下「前 3 个参与者」不会发出第 4 份

- **榜单的 bestPerUser（每人最高分）就是鹤立鸡群的 snapshot 口径** —— 这是**一致性红利**：两者可以复用同一个派生表，用户能对着榜单核对
  ⚠️ 唯一要补的是**排除本次提交**（打分结算时本行的 score 已经写进去了），照抄 leaderboard.ts 里 getBestExcluding 的写法
- **MAX_INVALID_PER_DAY / invalidCount** 保留（能量只管"成功计费的那次"，无效提交由它管）
- **能量口径与旧额度口径一致**：旧的是"失败不扣次数"，新的是"受理时锁、失败释放" —— 净效果相同，不是冲突
- **submissions.isConquered / articles.conqueredCount** 与成长体系无关，保留
- **补签把 lastReadDate 推到「今天 − 1」**，所以 readToday 仍然是 false —— 不会把「今天已读」算错
