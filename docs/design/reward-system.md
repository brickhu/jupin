# 奖励系统（设计稿）

> **状态：已确认，已实施**（连战记录页 + 领取模型见 7.4）。
> 与《成长体系与能量值》分开：那一份管「分数怎么涨」，这一份管「东西怎么发」。
> 相关：[growth-and-energy.md](growth-and-energy.md)

## 0. 一页看完

| | 内容 |
|---|---|
| **奖励什么** | **解冻卡**、**能量点** —— 就这两种 |
| **怎么配** | 规则表 + **封闭的触发器枚举**；规则可增删，但**下发只走同一个接口** |
| **最大的结构改动** | 解冻卡从「一个计数器 + 纯函数推导」改成「**一张卡一行 + 事件触发**」 |
| **消费模型的改动** | 解冻卡**不再自动消耗** —— 用户主动用，用了才产生使用记录 |
| **发放模型的改动** | 发下来 ≠ 到手：奖励先落成**待领取**，用户到「连战记录」页点领取才算持有，**有效期从领取那天起算**（见 7.4） |
| **两条硬约束** | ① **只有一个结算入口** ② **改配置不追溯** |
| **最容易错的地方** | 幂等：重放 / 补跑 / 并发都不能多发 |

## 1. 术语（这里一度写反过，写死）

- ⭐ **解冻卡**（unfreeze card）—— **不是「冻结卡」**。
  语义：连战断档后，用它把漏掉的那几天**解冻**、把连战续上。
  ⚠️ 代码里现在全叫 freeze（freezeCount / ❄️ 冻结卡），实现时要一并改名。
- **能量点**：整数点。每次挑战消耗 2 点；免费用户每日补足到 3 点；奖励 1 点。
- ⚠️ 奖励的计量单位一律是**点 / 张**，没有「次」这个单位。

---

## 2. 为什么要改成事件触发

现状（packages/shared/src/streak.ts）：

~~~
freezeEarnedBetween(before, after) = floor(after / 7) − floor(before / 7)
~~~

纯函数、不落库、随时可重算。它幂等，看起来很干净。

但「**规则要弹性可配置**」和它是**冲突**的：

> 把阈值从 7 改成 5 ⇒ 所有历史用户**立刻凭空多出几张卡** —— 而这是一次不可逆的发放。

⇒ 改成**事件触发**：发过一次就记一次，**永不重算**。
这条与「成长值不回溯」是同一条原则。

⚠️ 而现在还有一个必须改的硬理由：**解冻卡要有效期**。
「手上还有几张」已经不是一个整数能表达的了（每张卡有自己的到期日），
必须**一张卡一行**。

## 3. 数据模型

### 3.1 unfreeze_cards（一张卡一行）

| 列 | 说明 |
|---|---|
| id | |
| user_id | |
| granted_at | 发放时间（**只是记流水**，此刻还算不上「持有」） |
| **claimed_at** | **领取时间；null = 待领取**（见 7.4） |
| **expires_at** | **到期时间 = claimed_at + 1 年**；⚠️ **未领取时为 null** —— 有效期没起算 |
| used_at | 使用时间；null = 还在手上 |
| used_for_gap | 使用记录：补的是哪一次断档、补了几天 |
| rule_code | 哪条规则发的（可追溯到规则） |

⭐ 状态由两个时间戳决定：
**待领取** = claimed_at 为 null；**手上** = 已领取 + 未使用 + 未过期；**已用** = used_at 非 null。
**过期**由 expires_at 与「现在」比较得出，不落一个 expired 状态
（那需要定时任务去翻）。
⚠️ **待领取的卡不能用来补签** —— 必须先领（服务端判，不是靠端侧藏按钮）：
没领的卡是「还没生效的权益」，能直接用就等于没有领取这一步。

⭐ **消耗顺序：先到期先用**（FIFO by expires_at）——
否则用户的卡会先过期掉新的那几张，等于白送。这是标准的「食品柜」规则。

**余额**（手上几张、最早到期是哪天）**从表里现算**，
不在 users 上再存一个计数器 —— 那就是第二份真相，必然和卡表漂移。

### 3.2 reward_rules（可配置）

| 列 | 说明 |
|---|---|
| code | 规则标识，唯一 |
| trigger | 触发器（**枚举**，见第 5 节） |
| params | 结构化 JSON（阈值 / N 等） |
| reward_kind | unfreeze / energy |
| reward_amount | 张数 / 点数 |
| enabled | 开关 |
| starts_at | 生效时间 |
| daily_cap / lifetime_cap | 上限，防正反馈失控 |

### 3.3 reward_grants（发放流水）

| 列 | 说明 |
|---|---|
| user_id / rule_code | |
| ref_type / ref_id | 触发对象：submission / day / purchase |
| reward_kind / reward_amount | **快照**（规则后来改了也不影响历史） |
| created_at | |

⭐ **unique(rule_code, ref_type, ref_id, user_id)** —— 这就是幂等键。
重放、补跑、并发改配置，全靠它兜底。

⚠️ **ref_id 用 submission_id，不是 article_id**：规则 B 是「每次破纪录都发」，
用 article_id 做键会导致一个人在同一个句子上**一辈子只发一次**。

## 4. ⭐ 一个发放接口，规则可增删

这是这次设计的核心诉求：**规则可以随便加，但下发只有一条路**。

~~~
grantReward({
  userId, ruleCode, kind, amount,   // 发什么、发多少（来自规则表）
  refType, refId,                   // 触发对象（幂等键的一半）
  now,
})
  ① 查 reward_rules：规则不存在 / 已停用 / 未到 starts_at ⇒ 退出
  ② 查 reward_grants：幂等键命中 ⇒ 退出（发过了）
  ③ 查 daily_cap / lifetime_cap ⇒ 超了就退出
  ④ 写 grant（唯一键兜底并发）
  ⑤ 按 kind 落地：
       unfreeze → 插一行 unfreeze_cards（claimed_at = null ⇒ **待领取**，expires_at 也先留空）
       energy   → 加余额 + 写 energy_ledger
~~~

⭐ 新增一条**规则** = 加一行数据，**不动这个函数**。
⭐ 新增一种奖励**种类**（比如以后要发「皮肤」）= 只在第 ⑤ 步加一个分支。

## 5. 触发器枚举（封闭集合）

| trigger | 时机 | params | 预设用例 |
|---|---|---|---|
| streak_milestone | 本次读让 streakDays 跨过阈值 | threshold | 规则 A |
| sentence_top_exceed | 本次得分 **>** max(提交前的全场最高分, threshold) | threshold | 规则 B |
| daily_topup | 每日补足 | floor | 免费能量 |

⚠️ **加新触发点要发版，但不改求值器** —— 这是刻意的：
自由表达式引擎没法测、也没法向用户解释。而「弹性可配置」要的是
**阈值和数量**可配，不是**逻辑**可配。

## 6. 预设规则（目前就两条）

### A. 连续 7 天 → 1 张解冻卡

- trigger = streak_milestone，threshold = 7，reward = unfreeze × 1
- 判据 **>= 7**：首张第 7 天，之后每 7 天（**与现在的行为一致**，不会让老用户少卡）
- 实现：users 上新增 **unfreeze_marker_streak**（上次发卡时的 streakDays）

~~~
if (streakDays < unfreezeMarkerStreak) unfreezeMarkerStreak = 0   // 断档重来，计数从头
if (streakDays − unfreezeMarkerStreak >= 7) {
  grantReward(...)；unfreezeMarkerStreak = streakDays
}
~~~

### B. 破全场纪录 → 1 点能量

- trigger = sentence_top_exceed，threshold = 75，reward = energy × 1
- 判据：**本次得分 > max(提交前的全场最高分, 75)**（**严格大于**）
- ⭐ **不管是不是前 3 个参与者** —— 我们奖励的是**真正的破纪录者**
- ⭐ 与自我超越的基准**故意不同**：自我超越没有 75 下限，规则 B 有。
  两处不要「顺手统一」（见 growth-and-energy.md 第 10 节的注记）。
- 幂等：ref = submission_id ⇒ 可以反复触发（每次再破纪录都发），但每条提交只发一次。
- ⚠️ **严格大于** ⇒ **追平不算破纪录**，不发。
  （全场最高 96 分时，你再读一个 96 不发；97 才发。）
- ⚠️ 首读（全场还没人）时全场最高分 = 0 ⇒ 基准就是 75 ⇒ 读到 76 分以上才发。

## 7. 解冻卡怎么用：**用户主动，不自动**

⭐ 这是行为上的一个明确改动：**连战断档不再自动扣卡**。

### 7.1 现状 vs 新规则

| | 现状 | 新规则 |
|---|---|---|
| 断档时 | applyRead 里**自动**消耗卡补天 | **归 1，什么都不做** |
| 用户 | 事后才知道「卡被用掉了」 | **主动选择**用不用 |
| 使用记录 | 只有一个 freezeUsed 数字 | 每张卡一行，记清什么时候、补了哪一次断档 |

理由：卡是用户的资产。**自动花掉别人的东西**是这类系统最容易招骂的地方 ——
尤其它还是花很久攒的。

### 7.2 因此 applyRead 会变简单

~~~
if (lastReadDate === today)  → 不变（同一天读多遍只算一次）
if (lastReadDate 在未来)      → 不变（时钟回拨，不惩罚）
if (gap === 1)               → streakDays + 1
else                         → streakDays = 1      ← 不再自动用卡
~~~

### 7.3 补签（用卡的唯一途径）

用户看到「连战断了」→ 主动点「用解冻卡补上」→ 服务端：

~~~
gap    = daysBetween(lastReadDate, today)
missed = gap − 1                      // 漏掉的天数
需要   = missed 张卡
手上的卡（未过期、未使用）够吗
  够  → 按 expires_at 升序取 missed 张，写 used_at
        把 lastReadDate 往前推到「今天 − 1」（今天再读就是 +1，连战续上）
  不够 → 拒绝，并明确告诉他还差几张
        ⚠️ **不做部分补**：只补一半的话连战数字变得没法解释
        （与现有实现同一条原则：要么续上，要么重来）
~~~

⭐ **方案 a（已定）：补签只能在「断档之后、今天还没读」的时候做。**
今天一旦读过，连战已经归 1，「断档前的天数」就丢了，事后补不了。
好处是不用多存一个 streakBeforeBreak，规则也最好解释。

⚠️ **方案 a 有一个必须用 UI 兜住的坑**：**补签本身不增加天数** ——
它只是把缺口填上（把 lastReadDate 推到昨天）。**用户当天还得读一句才会 +1。**
如果补了签却没读，明天缺口又出现 1 天，还得再花 1 张。所以：

- 补签入口只在「今天还没读」时出现（服务端也要判，不能只靠端侧藏按钮）
- 补签成功后**立刻引导他读今天这一句**，别让卡白花
- 文案要说清「补上之后，今天读一句就接上了」，而不是「已恢复连战」

### 7.4 ⭐ 发放 ≠ 到手：**待领取**

奖励发下来时**不直接进背包**，而是落成一条**待领取**的记录；
用户到「**连战记录**」页点一下领取，那时才：写 claimed_at、把 expires_at 定成 **领取时间 + 1 年**。

为什么要有这一步（三个理由，都不是「为了做个领取按钮」）：

1. **有效期才不会白过。** 如果到期日从**发放**算起，一个三个月没回来的用户，
   回来时攒的那几张卡可能已经过期了 —— 而那些卡他压根没见过。
   从**领取**起算，等于「什么时候拿到手，什么时候开始算」。
2. **领取本身是一次回访。** 连战断档的用户最需要一个**回来的理由**，
   而「你有 2 张解冻卡待领取」正好是 —— 它把人拉回连战记录页，
   而那一页就摆着他的连战日历和「今天还没读」。
3. **发放和持有分开记账。** 发放是规则的事（可能补跑、可能重放），
   领取是用户的事（一定是一次明确的点击）—— 两者混在一个时间戳里，
   以后再想区分「发了没领」就再也分不出来了。

⚠️ 代价（要认）：**待领取的卡不算「手上」，也不能补签**。
所以服务端在两处都必须判 claimed_at：补签取卡时、以及「手上几张」的统计里。

⭐ 配套的页面是 **pages/me/streak（连战记录）**，三块自上而下：

| 块 | 内容 | 回答的问题 |
|---|---|---|
| ① 统计 | 连续战斗 N 天 + 大火苗 + 历史最长 | 我走到哪了 |
| ② 日历 | 一个月的格子：**连战日黄底 / 解冻日蓝底**，可翻月 | 我是怎么走到的 |
| ③ 领奖 | N 张解冻卡待领取 + 领取按钮 | 还有什么没拿 |

⚠️ 这一页**不落任何表**：连战日从 submissions 现算、解冻日由卡的 used_at 与 used_for_gap 反推
（见 services/streak-record.ts）。存一份「日历」就是第二份真相，迟早和提交记录对不上。
⭐ 入口有**四个**，都指向同一个页面（一处数据、多处入口，不各做一份）：

| 入口 | 位置 |
|---|---|
| 连战天数 | 首页**我的状态卡**第三格（与「参与场次」「挑战回合」并列的那一排） |
| 连战卡 | 首页下方那一整张（整张可点） |
| 🔥 连战记录 | 全局用户面板（左上角头像拉开）的菜单里 |
| 连战记录 | 「我的主页」里的战绩入口行 |

⚠️ 面板菜单里只放**现成的**页面 —— 放一个「敬请期待」会教会用户不再相信这个菜单。

## 8. 两条硬约束

### ① 只有一个结算入口

打分成功时调用**一次** settle(userId, submission)：

~~~
① streak（只算天数，不碰卡）
② 三个成长指标 + 快照落库
③ 奖励规则求值 → 全部走 grantReward(...)
~~~

⚠️ **轮询、幂等重放、任务接管都不结算** —— 否则同一次挑战会被结算多次、重复发奖。
（打分是异步的、结果由轮询取回，这条路径上有很多「再来一次」的机会。）

### ② 改配置不追溯

规则只对**生效之后**的事件生效。改配置 = 停旧规则 + 起新规则。

⭐ 这是「必须落库」的根本原因，也是唯一能让运营放心改数字的前提。

---

## 9. 上限（防正反馈）

奖励发能量 ⇒ 多读 ⇒ 更多提交 ⇒ 更多奖励，这是一条**正反馈**。
每条规则都要有 daily_cap / lifetime_cap。
规则 B 因为是**严格大于**、且基准会随全场成绩一起抬高，天然会收敛（越往后越难破）；
反而是规则 A 那种「每 7 天必发」的更该配额度。

## 11. 测试清单

- **幂等**：同一条 submission 重复结算 ⇒ 只发一次
- **并发**：同一条规则的两次并发求值 ⇒ 只发一次（unique 键兜底）
- **不追溯**：改阈值之后，历史 grants 不变
- **规则 A**：跨 7 / 14 / 21 各发一张；断档后 marker 归零、重新从 7 起算
- **规则 B**：得分**恰好等于**基准时**不发**（严格大于）；首读（全场最高 = 0）时基准是 75
- **补签（方案 a）**：今天已经读过之后再调补签 ⇒ 拒绝；补签成功后 lastReadDate 变成昨天
- **有效期**：过期的卡不计入「手上有几张」，也不能被补签选中
- **消耗顺序**：先到期先用（FIFO by expires_at），不是先进先出
- **不自动消耗**：断档后 streakDays 直接归 1，**卡表一行都不变**
- **补签**：卡不够时拒绝且**一张都不扣**（不做部分补）
- **结算只发生一次**：轮询 N 次、幂等重放 1 次之后，grants 数量不变
